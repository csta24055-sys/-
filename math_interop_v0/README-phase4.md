# 第4段階：DAG計算依存関係・永続キャッシュ・再計算・統合検証

第1〜3段階から独立した計算管理層の実験。建築LCA研究は再開せず、合成データのみを利用する。前段の共通 Math IR 0.1と第2段階の誤差型・計算機能を再利用する。

## 処理構造

5ケースについて `source -> exact(SymPy) -> numeric(NumPy) / high(mpmath) -> validated` を構築し、`SciPy`の数値積分結果を加え、`DuckDB`に厳密分子・分母を文字列のまま保存して単位別に集計する。

厳密値と浮動小数点近似を区別する。`SciPy`の推定誤差は保証区間ではない。単位は保存・比較するが、一般的な単位次元演算は未実装。

各ノードの内容アドレスを、計算内容・エンジンのバージョン・依存ノードのキー・入力の正規JSONから決定する。キャッシュ本体にはデータのSHA-256も保持する。内容の破損を検出したら**黙って再利用・修復しない**。欠落キャッシュは必要なノードだけ再計算。

## CIの合格条件

1. 27ノードの初回実行で27ノード全部を計算する。
2. 同じ入力の別プロセス実行で、27ノードすべてがキャッシュ再利用となる。
3. 1つの合成入力だけを変更すると、当該入力とその子孫6ノードのみを再実行し、残り21ノードを再利用する。
4. NumPyのエンジンバージョン識別子が変わると、それに依存する11ノードだけが再実行される。
5. 保存済みキャッシュの数値改ざんを検出して停止する。
6. キャッシュファイルが欠落している場合、そのノードだけを再実行する。
7. GitHub Actionsで既存の第1〜3段階の検証もすべて通す。

## 制限

- 現在は研究用の小規模な「単一プロセス書込み」プロトタイプ。並列マルチライターのロック、長期保存ポリシー、成果物の遠隔共有キャッシュ、数学全般の証明保証は未実装。
- NumPyのバージョン変更テストは**バージョン識別子の模擬変更**であり、異なるNumPy実行バイナリを用いたテストではない。
- SHA-256は偶発的・不正な変更の検出に利用する。攻撃者がハッシュと内容を両方書き換えた場合の真正性を保証する署名ではない。
- 未信頼の任意Pythonコードや任意のGitHubワークフローを実行する汎用サービスではない。
- MATLAB/SageMathの遠隔実行は第3段階のワークフローで検証し、第4段階自体はPythonのDAG管理を検証する。
