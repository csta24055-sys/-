# 12_APP_BASE：建築 LCA アプリの基礎システム（②④⑤）

2026-11-12 の開発指示書「建築LCAアプリ・基礎システムの実装（②④⑤限定）」による。作るのは次の 3 つだけで、計算そのものは
既存の 2 構造エンジン（[11_UNIFIED_SYSTEM](../10_TRANSFORM_STUDY/11_UNIFIED_SYSTEM/README.md)、`tstudy/unified.py`）を呼ぶ。

| | システム | 役割 | 主なファイル |
|---|---|---|---|
| ② | 共通入力データ・行列変換 | 入力 JSON → 共通内部形式 → エンジンの入力（シナリオ） | `lcaapp/common.py`、`convert.py`、`binding.py`、`schema.py` |
| ④ | 計算結果表示 | エンジンの結果から、指標・段階別・時間変化・注記の画面を作る | `lcaapp/view.py`、`render.py`、`web.py` |
| ⑤ | データ保存・管理 | 建物、入力の版、計算条件、計算結果、参照データを SQLite に保存 | `lcaapp/store.py`、`refdata.py` |

3 つをつなぐのが `lcaapp/service.py`（取り込み → 変換 → 計算 → 保存 → 表示）。使っているのは Python の標準ライブラリと、
エンジンがもともと使う NumPy だけで、Excel・表計算・マクロは使わない。

## 大事な前提

- **エンジンは独立概念モデル（70 評価単位）で、検証は架空データだけ**。J-CAT の再実装ではなく、他のツールとの一致や、実在の建物に対する
  精度を示すものではない。画面にも毎回この注記を出す。
- [第1章](../01_COMPLIANCE/README.md) は引き続き守る。原版の原単位・数式・マクロは含まない。同梱の数値（`samples/`）はすべて架空。
- 第9章・第10章の研究指示にあった「アプリは作らない」は研究段階の指示で、この章は上の開発指示書による。
- エンジン（第10章）、凍結済みの基準計算と生成器（第9章）、第1〜8章は変更していない。この章はそれらを読むだけ。
- ①入力画面と③数学エンジンは対象外。入力は、開発者用のコマンドか画面の貼り付け欄から JSON で与える。

## 起動と使い方

作業フォルダは `whole-life-carbon-jcat-study/12_APP_BASE`。保存ファイルは既定で `var/lcaapp.sqlite3`（Git には入らない）。
`--db <ファイル>` または環境変数 `LCAAPP_DB` で変えられる。

```bash
cd whole-life-carbon-jcat-study/12_APP_BASE

# 1) 架空の参照データと架空の建物 1 棟を保存する（検証用）
python3 -B -m lcaapp demo

# 2) 計算する（評価期間 60 年）。結果は保存される
python3 -B -m lcaapp calc 1 --period 60

# 3) 画面で見る  →  http://127.0.0.1:8765/
python3 -B -m lcaapp serve

# 保存済みの結果をもう一度表示する（再計算はしない）／HTML や JSON に書き出す
python3 -B -m lcaapp show 1 --html result.html --json results.json

# 自分で用意した入力 JSON を使う
python3 -B -m lcaapp refset add samples/refset_fictional.json
python3 -B -m lcaapp import samples/input_fictional.json --name "試験の建物"
python3 -B -m lcaapp projects
```

画面は 3 種類：建物プロジェクト一覧（参照データの一覧、架空データの作成、入力 JSON の取り込み）、建物のページ（入力の状態、計算条件の指定、
保存済みの結果の一覧、入力の更新）、計算結果のページ。サーバーは自分の PC の中だけで待ち受ける（127.0.0.1）。

## ② 入力データの形式と変換

入力文書（`lca-input/1`）。項目は分類の ID で指す。

```json
{"format": "lca-input/1", "data_kind": "fictional", "title": "建物の名前",
 "reference_set": {"name": "fictional-demo", "version": "seed-4201"},
 "categories": {
   "<大分類>": {
     "items":  {"<項目ID>": 2916.1, "<項目ID>": {"value": 2.5, "unit": "t"}, "<項目ID>": null},
     "tables": {"<表ID>": [{"<列ID>": 12.5, "@tables": {"<入れ子の表ID>": [{}]}}]},
     "others": [{"label": "その他の内容", "value": 3.2, "unit": "t", "note": "備考"}]
   }}}
```

| 状態 | 入力での書き方 | 共通形式 | エンジンへ渡す値 |
|---|---|---|---|
| 入力あり | 値 | `entered` | その値 |
| ゼロ | `0` | `zero` | 0 |
| 未入力 | `null`、空文字、項目を書かない | `missing` | 値なし（None）。ゼロにはしない |
| 存在しない | `{"state": "absent"}`、空の表 `[]`、行に `"@state": "absent"` | `absent` | 表・行は「行なし」。単独の値は値なし（エンジンに区別を渡す手段がないため。注記に出す） |
| 使えない値 | 型違い、語彙外、換算できない単位など | `invalid` | 値なし。元の値は保存し、未対応として一覧に出す |

- 単位：値に付いた単位が項目の単位と違うときは、参照データの換算の定義（kg↔t など）にあるものだけ換算し、記録する。定義がなければ使わない。
  数量のように単位そのものが入力の項目は、値に付いた単位を単位の項目へ入れる（食い違えば使わない）。
- 「その他」：内容をそのまま保存し、建物のページと結果の注記に出す。数値化して計算に入れることはしない。
- 分類にない ID、形の違う部分：捨てずに「未対応の入力」として保存・表示する。
- 補うのは 1 種類だけ：一定・直線・段階といった記述子で決まる年次表（モデルが「記述子の写し」と定めているもの）を、記述子から展開する。
  それ以外の値は作らない。空の入力からは数値が 1 つも生まれないことをテストで確認している。
- 必須項目（これがないとエンジンが評価できない。2026-11-12 に入力を 1 つずつ欠かして測定）：用途別面積、資材の区分、廃棄経路の名前、
  電力係数の年次表・施工時の係数・段階の値、上水・下水・一般廃棄物の年次表。欠けていれば計算せず「計算していない」と理由を保存する。
- 変換は入力の版ごとに 1 回。共通形式は保存し、エンジンの準備（共通表・積和①・節点スペクトル）もプロセス内で使い回すので、
  評価期間だけを変えた再計算は準備をやり直さない（架空の 200 行の建物で、初回 約 0.4 秒、2 回目以降 約 0.03 秒）。

エンジンが使う行列・配列・添字表は、エンジン自身（`tstudy/tables.py`、`tstudy/index.py`）がシナリオから作る。ここでは作り直していない。
渡った表の規模（表の数、列の数、資材・設備・係数の行数、節点の数）は、計算ごとに記録して結果画面の「計算の記録」に出す。

## ④ 結果画面に出るもの

数値はすべて、保存した計算結果から読む。各数値に出所のキーを添える。エンジンが値を返さなかった指標は「未計算」と表示し、数字は出さない。

| 表示 | 出所（エンジンの結果のキー） |
|---|---|
| ホールライフカーボン総量 | `SUM-03.value`（t 換算は `SUM-06.value`） |
| アップフロント（A1〜A5） | `SUM-01.value` |
| エンボディド（B6・B7 以外） | `SUM-02.value` |
| オペレーショナル（B6＋B7） | `X-02.by_stage` の B6 と B7 の和（表示側で行う計算はこの加算だけ） |
| 延床面積当たり、延床面積・年当たり | `SUM-04.value`、`SUM-05.value` |
| 段階別（A1-A3〜C4 の 14 段階）と割合 | `X-02.by_stage`、`SUM-07.by_stage` |
| 時間変化（年ごと・累積）のグラフと表 | `X-07.by_year`、`X-07.cumulative` |
| 基準案との比較（指定したとき） | `SUM-08` |
| 入力と計算の点検 | `SYS-01`〜`04`、`QA-01`〜`04`、`C-05` |
| 注記 | モデルの位置づけ、データの種別、参照データ、不完全な合計、未入力・存在しない・使えない値の数、「その他」、未対応の入力、数値の警告 |

合計に欠けがあるとき（エンジンの `complete` が偽）は、値に「不完全」の印を付ける。注記は計算が終わってから整理しており、計算の中に品質評価の
仕組みは足していない。

## ⑤ 保存の構造（SQLite、1 ファイル）

| 表 | 内容 |
|---|---|
| `projects` | 建物プロジェクト（名称、データの種別、作成・更新日時） |
| `input_versions` | 入力の版。入力文書そのもの、共通形式、状態の集計、使った結び付けの ID と版。更新は新しい版になり、前の版は残る |
| `other_items` | 「その他」の入力（分類、名称、値、単位、備考、元の内容） |
| `conditions` | 計算条件（評価期間、参照データ、基準案） |
| `runs` | 計算結果（70 単位の結果そのもの、画面用のデータ、変換の記録、状態 `ok`／`blocked`／`failed` と理由、所要時間） |
| `reference_sets`、`reference_items` | 参照データ（排出原単位、ガスと GWP、単位換算、物価指数、標準値の置き場）と、その種別・使用許諾の宣言・出典 |

- 結果ごとに「版の記録」を持つ：アプリの版、エンジンと入力モデルのソースの SHA-256（検証時と同じかどうか）、積和のステップ数、Python・NumPy の版、
  入力の SHA-256、結び付けの ID と版、参照データの名前・版・SHA-256。
- 参照データとして登録できるのは 2 種類だけ：`fictional`（すべての係数に架空のタグがあること）と、`licensed`（登録する人が使用許諾を確認したと宣言し、
  出典を書いたもの）。アプリは許諾の真偽を確かめられないので、宣言を記録するだけである。**他のツールの原単位などを無断で登録しないこと。**
  同梱しているのは架空データだけ。`standard_values`（標準値）は置き場だけあり、いまのエンジンは使わない。

## 未対応の項目と制約

1. 入力分類ファイルが未入手のため、5 つの大分類との対応づけは未実施（上の「入力分類ファイルについて」）。
2. 実在の排出原単位は入っていない。計算に使えるのは登録した参照データだけで、同梱は架空データのみ。実建築物の結果の妥当性は対象外。
3. エンジンの語彙にない値（例：モデルにない建物用途や資材の区分）は「使えない値」として計算に渡さない。
4. 「存在しない」を単独の値についてエンジンへ伝える手段はなく、値なしとして渡す（ゼロとして数えたい場合は 0 を入力する）。
5. 極端に大きい数値（1e308 など）では結果が有限でなくなる。その値は「未計算」として保存・表示し、注記に出す。
6. 共通形式は行数に比例して大きくなる（資材 2,000 行で約 7 MB、圧縮して保存）。2 万行規模は動作確認していない。
7. 画面は 1 人が自分の PC で使う前提（認証なし、同時書き込みの考慮なし）。入力の削除・建物の削除の機能はない。
8. 評価期間は年次表の長さ（130 年）まで。
9. 保存ファイルの構造を変えたときの移行の仕組みはない（版が違うファイルは開かずにエラーにする）。
