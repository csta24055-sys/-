# C 分類（収益・利益追求型の商用アプリ）— 共通する優れた設計原則

対象題材: （仮称）AirLCA Cloud — 中小の設計事務所・工務店・オフィス管理者向け SaaS（室内空気質センサーのモニタリング＋建材 LCA レポート自動作成）。料金・数値はすべてダミー。

## 根拠と確認レベル

- 根拠: 調査台帳 `data/ledger-C-1.json`（Notion / Linear / Canva / Figma / Stripe / freee会計）と `data/ledger-C-2.json`（SmartHR / Airtable / Slack / Vercel Geist / Duolingo / Miro）の計 12 件。
- 確認レベル: 台帳では全件 `fetched_official_page`。ただし取得できたのは主に**料金ページ・公式ドキュメント・デザインシステム文書のテキスト**で、**アプリ本体の画面構成や配色の多くは事前知識による推測**（台帳の verification_note に明記）。Canva の料金ページは 403 で取得できていない。本書の原則のうち、料金・無料体験・課金対象に関するものは「取得確認」の記述に基づく。画面レイアウトに関するものは推測が混じるため、根拠の強さを各項目の【根拠】に併記した。
- 本書では台帳以外の画面を見ていない。既存製品の画面を複製せず、原則だけを取り出している。

## 共通する優れた設計原則（11 項目）

### 1. 「最初の成果物」までの距離を設計目標にする
白紙から始めさせず、用途別テンプレートや既存データの取り込みで、登録当日に 1 つの成果（AirLCA なら「今月の空気質レポート」「建材 3 案の CO2 比較表」）を手に入れられるようにする。初見での価値理解は説明文ではなく成果物で起こる。
- 【根拠】Canva（テンプレート起点で最初の成果物が短い／推測含む）、Notion（テンプレートで初期設定が軽い／取得確認）、freee会計（過去データ 1 期分のインポート代行で乗り換え障壁を下げる／取得確認）。反例: Notion・Miro の白紙／無限キャンバスは何から始めるか迷いやすい（台帳の弱み欄）。

### 2. 無料枠は「量」で区切り、データは人質にしない
無料プランの制限は「センサー 3 台」「レポート月 1 件」のように数えられる量で示し、上限を超えても既存データは閲覧・書き出し可能に保つ。上位移行は「成長したから必要になった」と感じられる形にする。
- 【根拠】Linear（チーム数 2・課題 250 件など量で区切る／取得確認）、Airtable（上限超過でもデータは削除されず追加できなくなるだけ／取得確認）、Miro（直近 3 ボードは編集可能という明快な制限／取得確認）。反例: Slack 無料プランの 1 年後データ削除（取得確認）。

### 3. 無料体験の条件は登録ボタンの隣で言い切る
「クレジットカード不要」「試用期間後に自動課金しない」「データは有料移行後も引き継ぐ」「月払い／年払いの差額」を CTA の直近に置く。不安の除去そのものがコンバージョン施策になる。
- 【根拠】freee会計（3 条件を明記、CTA に「クレジットカード不要」／取得確認）、Miro・Notion（月払い／年払い切替と割引率を明示／取得確認）。

### 4. 推奨プランは 1 つだけ。比較表は標準語彙と数値差で書く
プランは 3 段階程度に抑え、推奨を 1 つだけ示す。比較表のセルは「含む／制限付き（数値）／アドオン／要相談」の決まった語彙で書き、○×だけで終わらせない。推奨には理由（例: 「センサー 4 台以上なら Pro」）を添える。
- 【根拠】Notion（Recommended を 1 プランのみ／取得確認）、Slack（Included / Add-on / Upon Request のセル表記／取得確認）、Linear（API レート 標準／2 倍／5 倍など数値差／取得確認）。反例: freee の 5 段階プラン、Figma の 3 軸料金（台帳の弱み欄）。

### 5. 課金は「価値を生む役割」にだけかけ、共有を獲得の経路にする
編集者・管理者に課金し、閲覧者・レポートの受け取り手（施主、テナント、上司）は無料にする。共有リンクで受け取った人が製品に触れることが、そのまま新規獲得につながる。
- 【根拠】Airtable（編集権限のあるユーザーのみ課金、閲覧・フォーム送信は課金しない／取得確認）、Figma（Full / Dev / Collab のシート種別で役割別の安い席／取得確認）。

### 6. ホームは「状況の要約＋次の 1 手」
ダッシュボードのホームには、主要な数値と「対応が必要なこと」をまとめ、次の行動を 1 つ示す。機能の一覧ではなく、利用者の今日の仕事から設計する。
- 【根拠】Stripe Dashboard（業績グラフと未解決の通知を 1 画面に集約、ウィジェットをカスタマイズ可能／取得確認）、Slack Block Kit（操作を段階に分け、必要な情報だけを出す／取得確認）。

### 7. 初心者のボタンと熟練者のショートカットを両立させる
主要操作は常に見えるボタンで提供し、同じ操作をコマンドパレットやショートカットでも呼べるようにする。低頻度の高度な操作は「その他」メニューへ。速さは継続利用者への価値であり、初心者を排除する理由にしない。
- 【根拠】Linear（キーボード中心の速さが製品価値／ただし初心者には学習コスト高）、Stripe（「?」でショートカット一覧、ピン留め・最近の履歴／取得確認）、Slack Block Kit（高度・低頻度操作はオーバーフローメニューへ／取得確認）。

### 8. 画面の前に「言葉」を設計する
LCA、GWP、CO2 濃度、換気量などの専門語を用語集として先に定義し、画面ラベル・プラン名・機能名・料金表で同じ言葉を使う。平易な日本語を優先し、開発者向け用語を管理画面に出さない。
- 【根拠】SmartHR Design System（「言葉からはじまるデザイン」を原則として明文化／取得確認）、freee会計（平易なラベル／推測）。反例: Stripe Dashboard に API・Webhook 等の用語が混在（取得確認）。

### 9. 色は「用途つきトークン」で定義し、ブランドと状態表示を両立させる
色の段階ごとに用途（背景／境界線／強調背景／文字）を固定し、状態色（良好・注意・要換気）もスケールとして持つ。状態は色だけでなく文言とアイコン形状でも示す。書体は日本語と多言語に対応するものを選ぶ。
- 【根拠】Vercel Geist（10 段階スケールに用途を割り当て／取得確認）、Canva Apps（色・アイコン・余白をトークン化／取得確認）、Slack Block Kit（色だけで意味を伝えない、ライト／ダーク両方でコントラスト確認／取得確認）、Miro Aura（多言語対応書体／取得確認）。

### 10. スマートフォンは「確認と即応」、デスクトップは「作成と分析」と役割を分ける
スマホは下部タブとタブ間で統一されたヘッダーで、アラート確認・現場メモ・レポート共有を片手で完結させる。重い LCA 編集はデスクトップに任せ、無理に同じ画面を縮小しない。
- 【根拠】Duolingo（下部コアタブ、統一ヘッダー体系／公式ブログで取得確認）、Stripe（iOS/Android アプリあり／取得確認）、Airtable Interface Designer（Desktop/Mobile プレビュー切替／検索結果で確認）。

### 11. 継続は「罪悪感」ではなく「蓄積される価値」で支え、指標で検証する
継続の理由は、履歴が増えるほど比較・予測が良くなる、レポートが自動で溜まる、といった蓄積価値で示す。小さな達成表示は控えめにし、デザイン変更はアクティベーション率・継続率・解約率で検証する。
- 【根拠】freee会計（「使うほどに、手作業がゼロに近づく」／取得確認）、Duolingo（再設計を指標で検証／取得確認。ただし損失不安を使う継続促進は反面教師）、Stripe（KPI をホームのウィジェットに集約／取得確認）。

## 避けるべき設計（7 項目）

1. **使ってから有料と気づかせる混在**: 無料の作業中に有料要素を区別なく混ぜ、完成直前に課金を迫る。有料機能は触る前にラベル（例:「Pro」）と価格を示す。【根拠】Canva の弱み（王冠マーク混在／事前知識）。
2. **期限・損失不安で決断を急がせる**: 「7 日以内なら 50% オフ」のカウントダウン、連続記録が途切れる恐怖を使った課金誘導、罪悪感を与える通知。【根拠】Slack の期限付き初回割引（取得確認）、Duolingo の弱み（中毒性・損失不安／一般的指摘）。
3. **無料ユーザーのデータを削除する・既定で広く公開する**: 計測データや施主の建物情報は機密になりうる。既定は非公開、削除ではなく「追加停止」で制限する。【根拠】Slack 無料プランの 1 年後削除、Miro 無料ボードの既定チーム公開（いずれも取得確認）。
4. **料金の分散と脚注への隠蔽**: 料金を別ページや問い合わせに分散させる、従量クレジットを脚注に置く、年払い前提の価格を月額のように見せる。【根拠】freee の製品ページに料金なし、Linear・Figma の AI クレジット注記、Figma の年払い前提表示（いずれも取得確認）。
5. **料金の軸・段階・数量制限の過多**: シート種別×製品×クレジットの多軸、5 段階以上のプラン、数量制限の羅列。【根拠】Figma、freee、Miro（取得確認）。
6. **白紙・高密度のまま初回画面を出す**: 何をすべきかわからない白紙、または熟練者向けの高密度一覧を初回に見せる。【根拠】Notion・Miro の白紙／無限キャンバス、Linear の高密度 UI（台帳の弱み欄）。
7. **解約を見つけにくくする・既存ブランドを模倣する**: 解約導線を登録導線より深くする（本プロジェクトでは解約は設定 → プラン から 2 操作以内、と定める）。また、Slack の紫・Vercel の白黒＋三角形・Duolingo のキャラクター等を真似て独自性を失う。【根拠】Stripe 台帳の「解約はホスト型ポータルで実装し解約妨害を避ける」、各台帳の avoid 欄。

## AirLCA Cloud に適用する計測設計（原則 11 の具体化・ダミー）

| 指標 | 定義（案） | 計測イベント |
|---|---|---|
| アクティベーション率 | 登録後 7 日以内に「センサー 1 台接続」かつ「レポート 1 件生成」 | `sensor_connected`, `report_generated` |
| 無料→有料転換率 | 登録コホートのうち 30 日以内に Pro/Team へ移行した割合 | `plan_changed(from,to)` |
| 4 週継続率 | 登録 4 週目に 1 回以上ログインまたはレポート閲覧 | `session_start`, `report_viewed` |
| 月次解約率 | 当月初の有料契約のうち解約した割合（解約理由は任意の 1 問） | `plan_cancelled(reason?)` |
| 共有起点獲得 | 共有リンク閲覧者のうち登録した割合 | `share_viewed`, `signup(source=share)` |

ダークパターン防止の受け入れ基準: 解約は 2 操作以内／試用終了の 3 日前に通知、自動課金なし／アップセルは常に「閉じる」が同じ大きさ／料金はすべて税込・月額と年額を併記。
