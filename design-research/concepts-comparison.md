# 成果物3: 12種類の UI コンセプト比較

4分類 × 各3案＝12案を横断して比較します。各案の詳しい仕様（画面構成・配色 HEX・技術・メリット/デメリット）と採点の根拠は、分類ごとの `concepts.md` を参照してください。設計原則の横断まとめは [design-principles.md](design-principles.md) にあります。

- 分類A 研究支援: [A-research-lab/concepts.md](A-research-lab/concepts.md)
- 分類B 公共: [B-public/concepts.md](B-public/concepts.md)
- 分類C 商用: [C-commercial/concepts.md](C-commercial/concepts.md)
- 分類D 大企業品質: [D-enterprise/concepts.md](D-enterprise/concepts.md)

**数値の扱い**: 本書の重みと点数は、全て各分類の `concepts.md` に書かれた値をそのまま写したものです。新しい点数は作っていません。加重合計は、各 `concepts.md` の採点表から Σ（点数 × 重み）÷ 100 で再計算し、12案全てで記載値と一致することを確認しました（食い違いはありません。今後食い違いが見つかった場合は `concepts.md` の値を正とします）。

**注意**: 重みは分類ごとに違うため、**加重合計点は同じ分類の中の3案を比べるためのもの**です。分類をまたいで点数の高低を比べること（例: B 案C 4.42 と A 案C 4.30）には意味がありません。

## 2. 分類ごとの評価の重み

各分類とも11基準・合計100%です。8つは全分類に共通の基準、3つは分類固有の基準です。

### 2.1 共通の8基準

| 評価基準 | A 研究支援 | B 公共 | C 商用 | D 大企業品質 |
|---|---:|---:|---:|---:|
| 操作効率 | 12% | 8% | 8% | 12% |
| 学習の容易さ | 8% | 10% | 10% | 8% |
| 情報の理解しやすさ | 10% | 12% | 10% | 10% |
| 視覚的完成度 | 4% | 5% | 7% | 8% |
| アクセシビリティ | 8% | 13% | 8% | 12% |
| 拡張性 | 8% | 6% | 6% | 10% |
| 実装・保守コスト（高得点＝低コスト） | 8% | 8% | 6% | 8% |
| 目的への適合性 | 12% | 10% | 10% | 10% |
| **共通8基準の小計** | **70%** | **72%** | **65%** | **78%** |

### 2.2 分類固有の3基準

| 分類 | 固有の基準1 | 固有の基準2 | 固有の基準3 | 小計 |
|---|---|---|---|---:|
| A 研究支援 | 正確性 12% | 再現性 12% | 操作速度 6% | 30% |
| B 公共 | 信頼性 10% | 透明性 10% | 公平性 8% | 28% |
| C 商用 | 収益化への貢献可能性 13% | 初回利用体験 12% | 継続利用のしやすさ 10% | 35% |
| D 大企業品質 | 一貫性 8% | 運用性 8% | セキュリティ設計 6% | 22% |

### 2.3 なぜ分類ごとに重みを変えたのか

同じ重みで12案を採点すると、「目的が違えば最適な UI も違う」という前提（[design-principles.md](design-principles.md) 第0章）が評価の段階で消えてしまいます。そこで、各分類の目的と失敗したときの損害の大きさに合わせて重みを配分しました（理由は各 `concepts.md` の重みの表に記載）。

- **A 研究支援**: 単位の取り違えや異常値の見落とし、条件の追跡漏れが研究成果を損なうため、**正確性・再現性**（各 12%）と、毎日の大量入力を支える**操作効率・目的への適合性**（各 12%）を重くしました。装飾より情報密度を優先する分類なので、**視覚的完成度は 4% と最も軽く**しています。
- **B 公共**: 高齢者・障害者・外国人住民・災害時を含む「誰一人取り残さない」ことが目的なので、**アクセシビリティを 13% と4分類で最も重く**し、健康・政策判断の誤認を防ぐ**情報の理解しやすさ**（12%）を次に置きました。公共用途では速さより誤りなく理解できることを優先するため、操作効率は 8% です。分類固有として信頼性・透明性・公平性を加えました。
- **C 商用**: 初回体験と収益化が事業の成否を直接左右するため、**収益化への貢献可能性（13%）と初回利用体験（12%）**を重くしました。分類固有の3基準の合計（35%）は4分類で最大です。実装・保守コストと拡張性はやや軽く（各 6%）しています。
- **D 大企業品質**: 長期運用・多組織・多ロールが前提なので、運用担当の日常業務を支える**操作効率**と、公共機関を含む利用者への責務としての**アクセシビリティ**（各 12%）を重くし、組織・機能が増え続けることから**拡張性を 10% と4分類で最も重く**しました。分類固有の一貫性・運用性・セキュリティ設計に合計 22% を配分しています。視覚的完成度は成熟度の一部として 8% です。

## 3. 分類ごとの採用案と、不採用案から取り込む要素

### 3.1 分類A 研究支援 — 採用: A-C「Pipeline Ledger」（4.30）

**採用理由**
1. 分類固有の正確性・再現性と目的への適合性（合計 36%）で、全て最高点（5点）。「計算根拠と使用データの追跡」「変更履歴と再現性」に最も直接に応える。
2. 既存リポジトリの Math IR パイプライン（SymPy / SageMath / MATLAB）と LCA 演算子が段の連鎖として実装されており、その構造をそのまま UI の骨格にできる。
3. 弱点の実装コスト（2点）は、台帳グリッド → 段のリストとジョブモニター → 根拠パネル → レポートの段 の順に部品を段階的に作って分散する。

**不採用案から取り込む要素**
- A-A（Grid Ledger）から: 「台帳」タブのデータグリッド（列のスキーマ検証、tabular-nums、集計行、数字キーのタグ）、学部生向けの既定画面を「測定入力」の段のグリッドにする、CSV・Excel の往復、保存検索
- A-B（Evidence Notebook）から: 「レポート」の段の出力を根拠ページ（説明・数式・図・表）として自動で組み立てる、軽い計算のスライダーによる即時の感度分析、図の代替の表、論文用の書き出しプリセット、スマートフォンでのコメントレビュー

### 3.2 分類B 公共 — 採用: B-C 段階的開示「3層レイヤー型」（4.42）

**採用理由**
1. 市民と専門家の両立・透明性・公平性という B 分類の目的に、同一ページ・同一 URL・同一根拠で応える唯一の案。B-A・B-B はそれぞれ片方の利用者を別の場所に追いやり、World Bank の分断（X5）を再生産する。
2. 分類固有の信頼性・透明性・公平性の3基準全てで満点。第3層の根拠ブロックと条件付き URL で、行政・研究者・市民が同じ数値の出どころを確認できる。
3. JS 非依存のコア（全層展開で読める）と第1層だけの軽量表示により、災害時・低速回線でも B-A に近い頑健さを持つ。
4. 既存の Math IR パイプライン・LCA 演算子を、第3層の「計算式と条件の開示」として自然に接続できる。
- 感度の確認（`concepts.md` 記載）: アクセシビリティと学習の容易さの重みを各 +5 しても、B-C（約 4.37）は B-A（約 4.23）を上回る。

**不採用案から取り込む要素**
- B-A（タスク直行型）から: 第1層の文章・文字サイズ・タップ領域（本文 18px 相当、48px）、手続きの「1画面1問」（分析画面には適用しない: X6）、やさしい日本語版と災害時の第1層のみの軽量テキスト版、トップの4つの市民タスクボタン
- B-B（分析ワークベンチ型）から: 条件の URL 保持、表示中データと全データのダウンロード、API URL と Python/R のコード例、データの無い選択肢の無効化と理由の文字表示、第3層から入る「詳細分析モード」（リンクドビューと LCA 条件の JSON 編集。初期リリースには含めずロードマップに掲載）、専門家向けの表のセル単位の状態記号（速報・確定・推計）

### 3.3 分類C 商用 — 採用: C-C アウトカム・ハブ（4.37）

**採用理由**
1. 課金理由が UI の構造そのものに埋め込まれている。成果物（レポート）の件数とセンサー台数という数えられる量が使用量メーターとして常に見え、上位移行が「成長の結果」になる。閲覧者無料の共有で獲得経路も持つ。
2. 初回体験と継続を同じ情報構造で扱える。初回はテンプレートで1件目のレポート、2回目以降は「今月のレポート」の更新という同じ動線になる。
3. 料金・試用条件・解約導線を1か所（設定 → プラン）に集約し、上限到達時もデータを消さない方針を UI 文言で約束できるため、ダークパターンを構造的に避けやすい。
4. 初回利用体験の単独点は C-B（5点）が上回るが、C-B は実装コスト・アクセシビリティの弱さ・日常業務の遅さが継続率・解約率に響くと判断した。

**不採用案から取り込む要素**
- C-A（ワークベンチ）から: `Ctrl+K` コマンドパレットとショートカット、ピン留め・最近の履歴、文脈サイドパネル内の高密度表（「詳細表示」切替）、インライン編集と賢いデフォルト値、等幅数値（熟練者の継続と Team 席の拡大を支える）
- C-B（ショーケース）から: 共有リンクで開く施主向けサマリーの視覚表現（SVG 平面図の部屋別状態表示、建物シルエットの CO2e 積み上げ）をレポートテンプレートの1種として採用。ただし WebGL は使わず、必ず表の代替を付ける。公開ページの控えめな「AirLCA で作成」表示（閉じられる・誤認させない）

### 3.4 分類D 大企業品質 — 採用: D-C「Federated Shell」（4.36）

**採用理由**
1. 基盤の本質は「大学・自治体・建設会社が同じ基盤を異なる権限で共有する」ことで、スコープ（組織 › プロジェクト › 環境）を全画面で明示する D-C だけが、別組織のデータを承認するような誤操作を構造的に防げる。
2. 承認と監査が「3列目の証跡」として主要導線に入っており、値の出所（P12）・差分承認（P6）を後付けでなく骨格で保証できる。
3. 組織ブランドをアクセントトークンだけに限定し、各組織の受け入れやすさと状態色の全組織共通（X3 の回避）を両立する。
4. 機能追加はシェルと3列の骨格に載せるだけで済み、長期運用の限界コストが低い。
- 弱点: スコープの学習コスト（学習の容易さ 3点）と実装コスト（3点）。新規参加者5名程度のタスクテストで確かめる。

**不採用案から取り込む要素**
- D-A（Operations Console）から: 列1のデータテーブル仕様一式（3段階密度、3状態ソート、一括操作バー、仮想スクロール、保存ビュー）、キーボード操作体系（`/` 検索、`j / k` 行移動、`g` 系ジャンプ）、スマートフォン版を当番対応用の縮退版（確認と承認に限定）にする割り切り
- D-B（Insight Workspace）から: スコープのホームに置く KPI カードと時系列・地図の概要表示（自由配置は不可、固定レイアウト）、全てのグラフに「表で見る」切替と要約文を必須にするルール、概要画面をそのまま PDF 化する報告用エクスポート、LCA シナリオ作成のステップ形式ウィザード

### 3.5 4分類の採用案に共通する傾向

4分類とも、採用されたのは基本軸の「統合型」に当たる案C でした。ただし統合の仕方は分類ごとに違い、**何を骨格にするか**がそれぞれの目的を表しています。

| 分類 | 採用案の骨格 | 骨格に選んだ理由（目的） |
|---|---|---|
| A | 計算パイプラインの段 | 再現性と計算根拠の追跡 |
| B | 結論 → 比較 → 根拠 の3層 | 市民と専門家の両立、透明性 |
| C | 作る成果物 | 初回価値・継続・収益化を1つの構造でつなぐ |
| D | スコープ（組織 › プロジェクト › 環境） | 多組織・多ロールでの安全な共同利用 |
