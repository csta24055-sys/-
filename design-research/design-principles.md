# 成果物2: 4分類の UI・UX 設計原則

本書は、4分類それぞれの `principles.md`（調査台帳 `research-ledger.md` の実在事例 48 件＝各分類 12 件から抽出）を横断してまとめたものです。各原則の詳しい説明・適用例・確認レベルは、分類ごとの原文を参照してください。

- 分類A（大学・研究室内部の研究支援アプリ）: [A-research-lab/principles.md](A-research-lab/principles.md)
- 分類B（国家規模・公共性の高いプロジェクト）: [B-public/principles.md](B-public/principles.md)
- 分類C（収益追求型の商用アプリ）: [C-commercial/principles.md](C-commercial/principles.md)
- 分類D（大企業品質のアプリ）: [D-enterprise/principles.md](D-enterprise/principles.md)
- 12 案のコンセプト比較（成果物3）: [concepts-comparison.md](concepts-comparison.md)

## 0. 方針: 4分類は同じデザインに統一しない

**目的が違えば、最適な UI も違う。** 4分類を1つの見た目・1つの画面構成に揃えることはしません。研究室の高密度な台帳画面を市民向けの公共サイトに持ち込めば高齢者が迷い、公共サイトの「1画面1問」を研究者の比較画面に持ち込めば作業が遅くなります（B の X6）。商用アプリの成果物中心のホームは、監査を伴う大企業の運用画面には合いません。

統一するのは「見た目」ではなく「土台」です（第3章）。アクセシビリティ基準、デザイントークンの仕組み、状態設計の4つ（読み込み中・空・エラー・成功）は全分類で共通にし、その上の画面骨格・情報密度・配色の性格・文言は分類ごとに変えます。

### 4分類の目的・主要利用者・最重要指標

| 分類 | 目的 | 主要利用者 | 最重要指標（評価の重みが最も大きい基準） |
|---|---|---|---|
| A 研究支援 | 測定・LCA・Math IR 計算の記録を、正確に・再現できる形で残し、指導と報告に使う | 学部生（入力）、大学院生（条件設計・比較・ジョブ実行）、教授（レビュー・承認） | **正確性・再現性・操作効率・目的への適合性**（各 12%） |
| B 公共 | 公的な環境データを、一般市民から専門家まで誰一人取り残さず、誤認なく伝える | 一般市民（高齢者・子育て世帯・呼吸器疾患のある人・外国人住民）、自治体職員、研究者・政策担当・データジャーナリスト | **アクセシビリティ**（13%）、**情報の理解しやすさ**（12%）、信頼性・透明性（各 10%） |
| C 商用 | 初回の価値体験と継続利用を通じて、無理のない有料化で収益を上げる | 小規模設計事務所・工務店の実務者、オフィス管理者、施主（共有リンクの閲覧者） | **収益化への貢献可能性**（13%）、**初回利用体験**（12%）。実運用ではアクティベーション率・転換率・継続率・解約率で検証 |
| D 大企業品質 | 多組織・多ロールの共同利用基盤を、長期にわたり一貫して安全に運用する | 運用担当者、承認者・監査担当、複数組織（大学・自治体・建設会社）の新規参加者 | **操作効率・アクセシビリティ**（各 12%）、分類固有の一貫性・運用性・セキュリティ設計（計 22%） |

重みの出典は各分類の `concepts.md` の評価表です（数値の一覧は [concepts-comparison.md](concepts-comparison.md) の第2章）。

## 1. 分類ごとの要約

### 1.1 分類A: 研究支援アプリ（[principles.md](A-research-lab/principles.md)：P1〜P11 / X1〜X7）

**設計すべき要素**
- 「選ぶ・一覧で見る・詳しく見る」の3領域を常に同じ位置に置く（P1）。根拠: Zotero、JupyterLab、ParaView、MATLAB
- 計算の依存関係（入力 → 処理 → 結果 → 図）を見える形で保ち、元データの変更時は「要再計算」を明示する（P2）。根拠: Origin、GraphPad Prism、KNIME、ParaView
- 処理の状態は少数の決まった語彙で、色・記号・文字の3つで示す（P3）。根拠: KNIME、eLabFTW、GraphPad Prism（反面教師）
- 重い計算は利用者が「実行」を決め、未適用の変更を強く見せる（P4）。根拠: ParaView（Apply の押し忘れ）、Observable
- 全ての記録・条件に版の履歴を持たせ、過去版の表示中は状態バナーを出す（P5）。根拠: LabArchives、Benchling、eLabFTW
- 入力は型と単位を持つスキーマで受け、入力時点で検証する（P6）。根拠: Benchling、GraphPad Prism、eLabFTW、LabArchives
- 1行=1試行の比較表と、表と図の色の一致（P7）。根拠: Weights & Biases、Zotero
- 研究室標準のテンプレートと役割別権限（P8）、GUI 操作の式・スクリプト化（P9）、説明・数式・図・表を1つの計算根拠ページに（P10）、開いた形式での入出力（P11）。根拠: LabArchives、eLabFTW、ParaView、MATLAB、Observable、Origin、Zotero

**避けるべき設計**
- 機能を全部初期画面に出す／アイコンだけのボタン（X1: MATLAB、Origin、ParaView）
- 実行順を自由にしすぎて隠れた状態を作る（X2: JupyterLab、Observable）
- 未適用・古い結果・過去版を目立たないままにする（X3: ParaView、LabArchives）
- 色だけで状態を表す、色の意味を利用者が自由に変えられる（X4: GraphPad Prism、eLabFTW、Zotero、KNIME）
- 数値データを自由記述や添付に埋もれさせる（X5: LabArchives、eLabFTW、GraphPad Prism）
- 詳細ペインの全展開・グラフの大量自動生成（X6: Zotero 7 ベータ、Weights & Biases）
- 企業向けの重い承認フローの必須化、外部クラウド保存の既定化（X7: Benchling、Weights & Biases、Observable）

### 1.2 分類B: 公共アプリ（[principles.md](B-public/principles.md)：P1〜P11 / X1〜X7）

**設計すべき要素**
- 「公式らしさ」ではなく運営主体の識別を全ページ最上部に固定する（P1）。根拠: SGDS（Masthead）、USWDS（Identifier）、DADS・GOV.UK・NHS・GC の模倣への注意
- 指標は「数値・区分名・色・意味・推奨行動」の5点セットで伝える（P2）。根拠: AirNow、GOV.UK、DADS
- 全ての図表に定型の根拠ブロック（出典・単位・更新日・管理者・引用方法）を付ける（P3）。根拠: Our World in Data、World Bank Open Data
- データの状態（速報／確定／欠損／推計）を正式な区分として表示する（P4）。根拠: 環境省「そらまめくん」、World Bank、AirNow、OECD Data Explorer（検索結果ベース）
- 同じ条件から図・地図・表・ダウンロード・API を生成し、URL で再現できるようにする（P5）。根拠: OECD Data Explorer、World Bank、Our World in Data
- 入口は「場所から」「指標から」の2軸、初期表示を空にしない（P6）。根拠: World Bank、GOV.UK、AirNow
- 一般利用者と専門家を同一ページの段階的開示で両立させる（P7）。根拠: NHS、Our World in Data、World Bank（反面）、SGDS
- 緊急時表示と JS 非依存のコア（P8）、多言語を初期要件に（P9）、意味トークンと部品単位のアクセシビリティ基準（P10）、原則・検証結果・終了計画の公開（P11）。根拠: DADS、USWDS、AirNow、GC Design System、東京都 新型コロナ対策サイト、GOV.UK、NHS

**避けるべき設計**
- 政府・公的機関のロゴ、公式バナー、書体、ヘッダー意匠の模倣（X1: GOV.UK / USWDS / DADS / NHS / GC / SGDS）
- JS が動かないと本文・表が空になる構成（X2: そらまめくん、OECD、World Bank）
- 状態を色だけで伝える、無効化の理由を出さない（X3: AirNow、OECD）
- 初期表示が位置指定待ちで空、回復手段が「全部やり直し」だけ（X4: AirNow、OECD）
- 全情報の縦積み、または目的別の別サイトへの分断（X5: Our World in Data、World Bank、そらまめくん）
- 申請フロー向けの「1画面1問」を専門家の分析画面に機械的に適用する（X6: GOV.UK、GC）
- 速報値・推計を確定値のように断定表示する（X7: NHS、そらまめくん）

### 1.3 分類C: 商用アプリ（[principles.md](C-commercial/principles.md)：原則 1〜11 / 避けるべき設計 1〜7）

**設計すべき要素**
- 「最初の成果物」までの距離を設計目標にする（1）。根拠: Canva、Notion、freee会計
- 無料枠は「量」で区切り、データは人質にしない（2）。根拠: Linear、Airtable、Miro
- 無料体験の条件は登録ボタンの隣で言い切る（3）。根拠: freee会計、Miro、Notion
- 推奨プランは1つだけ、比較表は標準語彙と数値差で書く（4）。根拠: Notion、Slack、Linear
- 課金は価値を生む役割にだけかけ、共有を獲得経路にする（5）。根拠: Airtable、Figma
- ホームは「状況の要約＋次の1手」（6）。根拠: Stripe Dashboard、Slack Block Kit
- 初心者のボタンと熟練者のショートカットの両立（7）。根拠: Linear、Stripe、Slack Block Kit
- 画面の前に「言葉」を設計する（8）。根拠: SmartHR Design System、freee会計
- 色は用途つきトークンで定義し、ブランドと状態表示を両立させる（9）。根拠: Vercel Geist、Canva Apps、Slack Block Kit
- スマートフォンは「確認と即応」、デスクトップは「作成と分析」（10）、継続は罪悪感ではなく蓄積価値で支え指標で検証する（11）。根拠: freee会計、Duolingo（指標検証。損失不安は反面教師）、Stripe

**避けるべき設計**
- 使ってから有料と気づかせる混在（1: Canva）
- 期限・損失不安で決断を急がせる（2: Slack、Duolingo）
- 無料ユーザーのデータ削除・既定での広い公開（3: Slack、Miro）
- 料金の分散と脚注への隠蔽（4: freee、Linear、Figma）
- 料金の軸・段階・数量制限の過多（5: Figma、freee、Miro）
- 白紙・高密度のまま初回画面を出す（6: Notion、Miro、Linear）
- 解約を見つけにくくする、既存ブランドの模倣（7: Stripe 台帳の注記、Slack・Vercel・Duolingo の avoid 欄）

### 1.4 分類D: 大企業品質アプリ（[principles.md](D-enterprise/principles.md)：P1〜P12 / X1〜X8）

**設計すべき要素**
- 色・余白・文字を「役割」で定義し、トークンを唯一の情報源にする（P1）。根拠: Atlassian、Material Design 3、Shopify Polaris、GitHub Primer、Salesforce SLDS 2（検索結果ベース）
- トークンを層（グローバル / セマンティック / コンポーネント）に分け、移行と自動検査を最初から用意する（P2）。根拠: SLDS 2、Atlassian、Primer、Fluent 2
- 個々の画面より先に画面骨格（フロアプラン / アプリシェル）を標準化する（P3）。根拠: SAP Fiori（検索結果ベース）、IBM Carbon、AWS Cloudscape、Ant Design
- 情報密度を利用者が選べる段階値にする（P4）。根拠: Carbon、Cloudscape、Fluent 2（反面）
- 空・読み込み・部分障害・完了・失敗・権限なしを一級の画面状態として設計する（P5）。根拠: Primer、Carbon、Ant Design、Cloudscape
- 確認ダイアログはリスクに比例させ、未保存変更を必ず守る（P6）。根拠: Cloudscape、Fiori、Polaris
- 強い注意を引く要素は1画面に1つ、操作系は内容より控えめに（P7）。根拠: Adobe Spectrum、Apple HIG / Liquid Glass 技術概要、Material Design 3
- 画面状態を URL と保存ビューで共有（P8）、アクセシビリティを部品と開発工程に埋め込む（P9）、幅に応じた段階的ナビゲーション（P10）、設計システム自体の版と成熟度（P11）、数値・単位・日時と「値の出所」の規則化（P12）。根拠: Cloudscape、Primer、Polaris、Fluent 2、Atlassian、Material Design 3、Spectrum、Fiori、Ant Design、Carbon

**避けるべき設計**
- 他社のブランド資産・画面構成の模倣（X1: 全12件、特に Fluent 2・Carbon・Fiori・Primer・Spectrum）
- 半透明素材・大胆な形状や動きを高密度画面に持ち込む（X2: Apple HIG / Liquid Glass、Material Design 3 Expressive）
- 状態色の意味をテーマ・壁紙・組織ブランドに連動させる（X3: Material Design 3、Fiori）
- データテーブルをスプレッドシート代わりにする・入れ子・狭い場所への押し込み（X4: Carbon）
- トースト・モーダルの多用（X5: Ant Design、Cloudscape）
- 補助パネルや多列表示の常時表示で主作業を圧迫する（X6: Cloudscape、Fiori）
- 移行途中・ベータの基盤に長期運用機能を依存させる（X7: SLDS 2、Spectrum）
- 抽象的な「価値」だけを掲げ、具体的な判断基準に落とさない（X8: Ant Design、Fluent 2 との対比）

## 3. 4分類に共通する土台

### 3.1 アクセシビリティ: WCAG 2.2 AA を下限にする
- 全分類で WCAG 2.2 AA を下限とします（B は JIS X 8341-3:2016 AA も満たす）。
- 文字のコントラスト 4.5:1 以上。状態は必ず「色＋記号（形状）＋文字」の3つで示す（A の X4、B の X3、C の原則 9、D の P1）。
- キーボードだけで全操作ができ、フォーカスが見えること。ランドマークと見出しの階層を持つこと。
- 図には代替の表と要約文を付ける。動きは `prefers-reduced-motion` に従う。

### 3.2 デザイントークン: 値ではなく役割で定義する
- 色・余白・文字・動きを、用途名（例: `color.text.subtle`、`status.danger.bg`）で定義する（D の P1、B の P10、C の原則 9）。
- 層はグローバル / セマンティック / コンポーネントの3つ（D の P2）。背景色と文字色はペア（on-X）で定義し、コントラストを構造的に守る。
- **状態色（成功・注意・失敗・データなし など）は全分類で意味を固定**し、ブランド色やテーマで変えない。分類ごとに変えるのは、ブランド・アクセント・密度・文字サイズの層だけ。
- ハードコード値を検出する Lint を最初から用意する。

### 3.3 状態設計: 読み込み中・空・エラー・成功を一級の画面状態にする

| 状態 | 共通の規則 | 分類ごとの重点 |
|---|---|---|
| 読み込み中 | スケルトン表示。長い処理は進行状況を示し、画面を固めない | A: ジョブモニターに実行中のジョブを表示し `aria-live="polite"` で読み上げ／D: 部分読み込みと再読み込み |
| 空 | 初期表示を空にしない。「まだ無い」と「条件に合うものが無い」を区別し、次の操作を示す | B: 既定で全国概況を表示（P6）／C: テンプレートで最初の成果物へ誘導（原則 1） |
| エラー | 何が起きたか・データはどうなったか・次に何をするかを文字で示す。色だけに頼らない | A: 失敗した段と該当セルへ移動／B: 無効化の理由を文字で表示／C: 上限到達でもデータは閲覧・書き出し可／D: 部分障害・権限なし（申請方法つき） |
| 成功 | 結果を内容の中で確認できるようにする。トーストだけで済ませない（D の X5） | A: 段の状態 ●成功 と来歴／C: 成果物の完成度バーの更新／D: 完了画面（Ant の Result） |

加えて、A の「要再計算」「未適用」「過去版を表示中」、B の「速報／確定／推計」、D の「権限なし」「部分障害」は、各分類で追加する状態として同じ仕組み（状態トークン＋記号＋文字）に載せます。

### 3.4 D（大企業品質）を A / B / C に重ねる方法

D の原則は「見た目」ではなく「品質を長期に保つ仕組み」なので、A・B・C の**下の層**として重ねます。画面の性格（密度・文言・配色の性格）は各分類のまま残します。

| D の原則 | A 研究支援に重ねる | B 公共に重ねる | C 商用に重ねる |
|---|---|---|---|
| P1・P2 トークンの層 | 状態語彙（○◐●✕↻）をセマンティックトークン化 | 大気質区分・データ状態をトークン化し、部品単位でアクセシビリティ基準を紐付け（B の P10 と一致） | ブランド色はアクセント層、Pro 表示は強調層、状態色は固定層 |
| P3 画面骨格の標準化 | 4領域（段・作業・根拠・ジョブモニター）を全画面の骨格にする | 識別帯 → 緊急時バナー → 層ナビ → 3層 をページ骨格として固定 | 左レール＋ステップ＋文脈サイドパネルを全成果物で共通にする |
| P4 密度の段階値 | 行の高さ 26px / 22px の切替を密度トークンにする | 第3層の表と詳細分析モードだけに適用（市民向けの層は低密度のまま） | 「詳細表示」切替を密度の段階値として実装 |
| P5 一級の画面状態 | ジョブの失敗・要再計算・過去版を状態として設計 | 欠損・測定停止・JS 無しの表示を状態として設計 | 上限到達・試用終了・支払い失敗を状態として設計 |
| P6 リスク比例の確認 | 条件の上書き・版の削除に確認。軽い操作には出さない | 通知設定の解除など、市民の手続きで未入力を守る | 解約は2操作以内のまま、データ削除だけに強い確認 |
| P8 URL と保存ビュー | ジョブ・条件の版を URL で開ける（再現性） | 条件付き URL（B の P5 と一致） | 共有リンクと保存ビュー |
| P11 版と成熟度 | 研究室テンプレートに版を付ける | 設計原則・更新履歴の公開（B の P11 と一致） | 部品の状態（ベータ等）を明示し、ベータ機能に課金導線を依存させない（D の X7） |
| P12 値の出所 | 図の下に「入力ジョブ・条件の版・ハッシュ」を表示（A の P2・P5） | 根拠ブロック（B の P3） | レポートの数値に元データと計算条件へのリンク |

**重ねるときに持ち込まないもの**
- A に D の重い承認・署名フローを必須として持ち込まない（A の X7）。承認は任意の機能にする。
- B の市民向けの層に D の高密度テーブルや多列表示を持ち込まない（D の X6、B の X6 の逆向き）。
- C に D の画面骨格を持ち込んでも、初回画面は高密度にしない（C の避けるべき設計 6）。
- どの分類でも、D の半透明素材や大胆な動きをデータ画面に入れない（D の X2）。
