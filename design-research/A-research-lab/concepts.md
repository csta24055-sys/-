# 分類A 研究支援アプリ: 3つの UI コンセプトと評価

前提: `principles.md` の P1〜P11（優れた原則）と X1〜X7（避けるべき設計）
題材（ダミー）: 室内空気清浄度の測定（PM2.5、CO2、浮遊粒子数、ISO 14644-1 クラス）、建材 LCA（CO2 排出量）の計算条件と結果、Math IR（SymPy / SageMath / MATLAB）計算ジョブの履歴

## 比較軸を変えた理由

基本の比較軸は「実用性 / 先進性 / 統合型」です。研究支援アプリでは、見た目の完成度の差よりも、**作業の単位（何を1つのまとまりとして扱うか）の差**の方が、正確性・再現性・作業速度に大きく効きます。台帳12件も、操作体系で3つの系統に分かれます。

| 系統 | 作業の単位 | 台帳の事例 |
|---|---|---|
| 表計算・台帳型 | 行（1測定・1試行） | Zotero, Weights & Biases, GraphPad Prism, Origin |
| ノートブック型 | 文書（説明・数式・図の流れ） | MATLAB Live Script, JupyterLab, Observable |
| パイプライン型 | 処理の段（入力 → 処理 → 結果） | KNIME, ParaView, Origin（依存関係） |

そこで、基本の3案に次のように対応させます。

- **案A = 表計算・台帳型**: 実用性・効率を重視
- **案B = ノートブック型**: 先進性・視覚的な完成度を重視
- **案C = パイプライン＋台帳の統合型**: A の一覧と B の根拠ページを、パイプラインの骨格でつなぐ

3案は配色の違いではなく、**主画面が何で、利用者が何を操作して前へ進むか**が違います。

## 案A: 表計算・台帳型「Grid Ledger」

### デザインの基本思想
「研究データは、まず表である」と考えます。全ての対象（測定セッション、LCA の条件セット、計算ジョブ）を、1行=1件の高密度な表で扱います。選択・編集・比較・書き出しを、全てその表の上で完結させます。Excel に慣れた研究者が、学習なしで使い始められることを最優先にします。（P1, P6, P7, P11）

### 想定利用者と主要タスク
- **学部生**: 測定値の入力・取り込み（CSV）、異常値の確認
- **大学院生**: 条件を変えた LCA の試行を比較、ジョブの再実行
- **教授**: 異常値とレビュー待ちのフィルタで一覧を確認し、承認する

### 代表的な画面構成（デスクトップ）
- **上部**: データセットの切替タブ（測定 / LCA / ジョブ）、フィルタ式の入力欄（`CO2 > 1000 and room = "B204"`）、表示列のプリセット
- **左（200px）**: 保存検索（「今週の異常値」「レビュー待ち」）、部屋・装置・プロジェクトのツリー、色付きタグ（最大6個、数字キーで付与、文字ラベル併記）
- **中央**: データグリッド。列は固定・並べ替え・グループ化ができる。セルの上で検証し、異常値は背景色＋⚠記号＋閾値ツールチップで示す。下部に集計行（平均、最大、n）
- **右（320px、折りたたみ可）**: 選択行の詳細を折りたたみセクションで表示（条件、来歴、版の履歴、添付）。既定では「条件」だけを開く（X6 を避ける）
- **下部**: 選択行のミニグラフ（時系列のスパークライン、または選択行の比較バー）

### ナビゲーション
- 一覧を起点にした平坦な構造: データセットのタブ → フィルタ → 行 → 右の詳細。階層は最大2段
- キーボード操作: ↑↓で行の移動、Enter で編集、`/` でフィルタ、`1`〜`6` でタグ、`Ctrl+K` でコマンドパレット

### 配色・フォント・余白
| 用途 | HEX |
|---|---|
| 背景 | `#FFFFFF` / 区切り線 `#D5DAE1` / 表のヘッダー `#EEF1F5` |
| 文字 | `#1A1D21` / 補助の文字 `#4A5361` |
| アクセント（選択・リンク） | `#1F5FA8` |
| 異常値 | 文字 `#B3261E`、背景 `#FDECEA`（＋⚠） |
| 注意 | 文字 `#8A5A00`、背景 `#FFF4DB`（＋△） |
| 正常・レビュー済み | `#1E6B3A`（＋✓） |
- フォント: `"BIZ UDPGothic", "Noto Sans JP", system-ui, sans-serif`。数値は `font-variant-numeric: tabular-nums`。ID とハッシュは `ui-monospace, "BIZ UDGothic", monospace`
- 文字サイズ: 本文 13px、表 12.5px。余白は 4px の倍数。行の高さ 26px（「詰めた表示」で 22px）

### 情報表示の密度
**非常に高い**。1画面に 30〜40 行 × 12〜20 列を表示します。

### グラフ・表・入力フォームの表現
- **表**: 主役。単位はヘッダーの2段目に固定表示（`PM2.5` / `µg/m³`）。条件付き書式は研究室が決めた閾値テンプレートだけを使う
- **グラフ**: 補助。下部パネルの小さな時系列グラフと、選択行の比較バー。行の色見本とグラフの線の色を一致させる（P7）
- **入力**: セルに直接入力する。型と範囲は列のスキーマで検証する。単位が違う貼り付け（mg/m³ など）は換算の候補を出す

### デスクトップとスマートフォンの違い
- **デスクトップ**: 3ペイン＋グリッド。編集と比較の全ての機能
- **スマートフォン**: 表を「カードの一覧」に変える（主要な3項目と状態だけ）。用途は、現場での測定値の1件ずつのフォーム入力、異常値の通知の確認、承認に絞る。グリッドの一括編集はできない

### アクセシビリティ
- グリッドは `role="grid"` と `aria-rowindex` で構成し、キーボードだけで全ての操作ができるようにする
- 異常値は色＋記号＋文字。フォーカスリングは 2px `#1F5FA8`
- 文字のコントラストは 4.5:1 以上。行の高さを切り替えて、ロービジョンの利用者が見やすくできるようにする

### 採用技術と実装難易度
- React + TanStack Table（または AG Grid Community）による仮想スクロール、Papa Parse / SheetJS で CSV・Excel 入出力、バックエンドは FastAPI（既存の Python の LCA 演算子と Math IR を呼ぶ）
- **難易度: 低〜中**。一番の難所は、グリッドのキーボード操作とスキーマ検証です

### メリット
- 学習コストが最も低い。大量データの閲覧・比較・異常値の確認が速い
- Excel・CSV との往復が自然にできる

### デメリット
- 計算の依存関係（どの結果がどの条件から来たか）が表だけでは見えにくく、再現性の説明が弱い（P2 が弱い）
- 図や根拠の説明は、別のツールに頼ることになる

## 案B: ノートブック型「Evidence Notebook」

### デザインの基本思想
「研究は、根拠を説明する文書である」と考えます。計算の前提・式・入力表・図・考察を、縦に流れる1つの文書（ノート）にまとめます。入力のウィジェットと図をリアクティブにつなぎ、条件を変えた影響を即座に見せます。ゼミの報告や論文図の作成まで、同じ画面で行います。（P4, P9, P10）

### 想定利用者と主要タスク
- **大学院生**: LCA の感度分析（係数のスライダー → GWP の図）、Math IR の式の確認と記述
- **教授**: 根拠ページを読み、セル単位でコメントを付ける
- **学部生**: テンプレートのノートの、入力欄だけを埋める

### 代表的な画面構成（デスクトップ）
- **上部**: ノートの題名、版の表示（`v5・レビュー待ち`）、「実行」ボタン（重いセルだけが対象）、共有ボタン
- **左（220px）**: 目次（見出しの一覧）と、セルの状態マーカー（● 最新 / ↻ 要再計算）
- **中央（最大 760px の本文の段）**: セルが縦に並ぶ。種類は、説明（Markdown）、数式（LaTeX 表示＋Math IR）、入力（スライダー・選択・小さな表）、図、表
- **右（280px）**: 変数インスペクタ。現在の変数・係数・単位の一覧と、各値がどのセルで定義されたか

### ナビゲーション
- 文書の中のスクロールと、目次からのジャンプが中心です。ノート同士は「ノートの一覧」のページから開きます
- 依存関係は、セルの左端の「依存の線」（クリックで上流のセルを強調）で示します。実行順は依存グラフで自動的に決め、手動の順番実行はさせません（X2 を避ける）

### 配色・フォント・余白
| 用途 | HEX |
|---|---|
| 背景 | `#FBFAF7` / セルの面 `#FFFFFF` / セルの枠 `#E2DED6` |
| 文字 | `#22252A` / 補助の文字 `#55595F` |
| アクセント | `#5B3FA8` |
| 図の系列 | `#2D6CDF` / `#C2571A` / `#2E8B57` / `#7A4FB5`（形の違うマーカーと併用） |
| 要再計算 | `#8A5A00`（＋↻） |
- フォント: 本文 `"Noto Sans JP", "Hiragino Sans", system-ui, sans-serif` の 15px、行間 1.7。数式は `"STIX Two Math", "Cambria Math", serif`。コードは `ui-monospace`
- 余白は 8px の倍数。セルの間は 24px

### 情報表示の密度
**中〜低**。読みやすさと図の大きさを優先します。1画面に 2〜4 セルです。

### グラフ・表・入力フォームの表現
- **グラフ**: 主役。幅いっぱいの大きな図に、信頼区間の帯と注記（例: 「WHO 指針 15 µg/m³（24時間平均）」の基準線）を付ける。論文用のプリセット（モノクロ可、300 dpi）で書き出す
- **表**: 図の根拠として小さく置く。全体の表は「データを開く」で別のタブに表示する
- **入力**: スライダーと数値欄の組を並べ、変更すると軽い計算は即時に、重い計算は「実行」で更新する

### デスクトップとスマートフォンの違い
- **デスクトップ**: 目次・本文・変数インスペクタの3段
- **スマートフォン**: 本文の1段だけの閲覧モード。図をタップして全画面で拡大し、セルにコメントを付けられる。編集と実行は行わない（教授が移動中にレビューする場面を想定）

### アクセシビリティ
- 見出しの構造で目次を自動生成する。数式には MathML と読み上げ用の文字を付ける
- 図には代替の表（「この図のデータ」）を必ず付ける。系列は色と形の両方で区別する
- 動きのある更新では `prefers-reduced-motion` を守る

### 採用技術と実装難易度
- Svelte または React + Observable Plot / Vega-Lite、KaTeX、Pyodide（軽い計算）、重い計算はサーバーの SymPy / SageMath / MATLAB へ投げるジョブ
- **難易度: 中〜高**。リアクティブな依存グラフと、サーバー計算のキャッシュ管理が難所です

### メリット
- 計算の根拠を説明する力と、図の完成度が最も高い。指導と報告に強い
- 感度分析のループが速い

### デメリット
- 大量の測定データを一覧・検索・一括編集する作業に向かない
- 自由度が高く、ノートごとに書き方がばらつきやすい。学部生には構造が見えにくい

## 案C: 統合型「Pipeline Ledger」（パイプライン＋台帳）

### デザインの基本思想
「研究は、入力 → 処理 → 結果の連鎖であり、その全段に台帳と根拠が付く」と考えます。画面の骨格を、**計算パイプラインの段**（データ取り込み → 検証 → Math IR 変換 → ソルバー実行 → LCA 演算 → 図表・レポート）にします。各段を選ぶと、その段にふさわしい表示（表・フォーム・図・根拠ページ）が中央に出ます。案A のグリッドと案B の根拠ページを、パイプラインの「段の表示」として取り込みます。（P1〜P11 を総合）

### 想定利用者と主要タスク
- **大学院生（主）**: 条件の設計、ジョブの投入、結果の比較、失敗した段の特定
- **教授**: パイプラインの状態の俯瞰、レビューと承認、版の差分の確認
- **学部生**: 「取り込み」と「検証」の段だけが開いた、テンプレートのパイプラインで測定データを入力する

### 代表的な画面構成（デスクトップ）
- **上部バー**: プロジェクト名、パイプラインの版（`v5`、過去版のときは全幅の状態バナー）、コマンドパレット（`Ctrl+K`）、「未適用 3項目 ▶ 実行」ボタン
- **左（240px）**: パイプラインの段のリスト。各段に状態（○ 未設定 / ◐ 準備完了 / ● 成功 / ✕ 失敗 / ↻ 要再計算）。上には「グラフ表示」の切替があり、段の依存関係を自動で整列した図として見られる（自由配置はしない）
- **中央**: 選択した段の作業領域。2つのタブを持つ
  - 「条件」: 型と単位を持つフォーム、または入力の表
  - 「出力」: 結果の表と図
- **右（300px）**: 根拠パネル。この段の入力の来歴（元ファイル・ハッシュ・版）、使った式（Math IR / SymPy の表示）、係数の出典、変更履歴、コメント
- **下部（折りたたみ可、160px）**: ジョブモニターと問題一覧。実行中・失敗・警告のジョブの一覧で、クリックすると該当の段とセルへ移動する

### ナビゲーション
- 主軸は**段の順序**（左のリスト。キーボードの `[` `]` で前後の段へ）
- 副軸は**台帳**です。上部の「台帳」タブで、全ジョブ・全測定の一覧（案A のグリッド）に切り替えます。1行を開くと、そのジョブのパイプラインの状態が復元されます
- 根拠ページ（案B）は「レポート」の段の出力として生成します。ノートを自由に書くのではなく、段の情報から組み立てます

### 配色・フォント・余白
| 用途 | HEX |
|---|---|
| 背景 | `#F4F6F8` / 面 `#FFFFFF` / 区切り `#CDD3DB` |
| 文字 | `#16191D` / 補助の文字 `#4A5361` |
| アクセント（選択・主要ボタン） | `#00687A` |
| 状態: 未設定 | `#5F6670`（○） |
| 状態: 準備完了 | `#8A5A00`（◐） |
| 状態: 成功 | `#1E6B3A`（●） |
| 状態: 失敗 | `#B3261E`（✕） |
| 状態: 要再計算 | `#6A3FB5`（↻） |
| 過去版のバナー | 背景 `#E8F0FB`、文字 `#1F3F73` |
- 状態色は、アクセントの色や図の系列の色と重ならない色相に固定します（X4 を避ける）
- フォント: `"BIZ UDPGothic", "Noto Sans JP", system-ui, sans-serif`。本文 13px、根拠パネル 12.5px、レポート段の本文 15px。数値は tabular-nums
- 余白は 4px の倍数。パネルの内側 12px、表の行 26px

### 情報表示の密度
**高い**（ただし、段の単位で区切られている）。左と下部で全体の状態を、中央で1段の詳細を見ます。

### グラフ・表・入力フォームの表現
- **入力フォーム**: 段の「条件」タブ。単位の表示、許容範囲、既定値、出典 ID の入力欄を1行にまとめる。変更した項目は左に紫の縦線と「未適用」の文字を付ける（P4）
- **表**: 「出力」タブと台帳。案A と同じグリッドの部品を使う
- **グラフ**: 「出力」タブとレポートの段。図の下に「この図の入力: ジョブ J-0412、条件 v5、データのハッシュ 3f9a…」を常に表示する（P2, P5）

### デスクトップとスマートフォンの違い
- **デスクトップ**: 4つの領域（段のリスト・作業・根拠・ジョブモニター）
- **スマートフォン**: 下部のタブを3つにする（ジョブ / 異常 / 承認）
  - 段のリストを縦のタイムラインとして表示し、状態の確認、失敗の通知、承認、再実行の指示だけを行う
  - 条件の編集は行わない。ただし学部生向けに「測定入力」の段だけはフォームとして開ける

### アクセシビリティ
- 状態は色・記号・文字の3つで表示する。段のリストは `role="tree"` または順序付きリストにする
- ジョブモニターの更新は `aria-live="polite"` で読み上げる。失敗は `assertive` にする
- 全てのパネルにランドマークの役割と見出しを付け、`F6` でパネルの間を移動できるようにする

### 採用技術と実装難易度
- React + TanStack Table、段の依存グラフは ELK.js の自動整列（表示だけ）、Vega-Lite、KaTeX
- バックエンドは FastAPI + ジョブキュー（RQ / Celery）。既存の Math IR パイプライン（SymPy / SageMath / MATLAB）と LCA 演算子を、段として登録する
- 版と来歴は、入力のハッシュと条件の版を DB（SQLite → PostgreSQL）に記録する
- **難易度: 高**。段ごとの表示部品、来歴の記録、再計算の判定が必要です。ただし、案A のグリッドと案B の図・根拠の部品を再利用できます

### メリット
- 正確性・再現性・計算根拠の追跡が最も強い
- 既存リポジトリの Math IR パイプラインの構造と、そのまま対応する
- 役割ごとに必要な段だけを見せる段階的な開示ができる

### デメリット
- 実装と保守のコストが最も高い
- 最初に「段」という考え方を理解する必要がある（学部生向けのテンプレートと、段階的な開示で緩和する）
- 単純な表の作業だけをしたい人には、1段多い操作になる（「台帳」タブで直接グリッドへ行けるようにして緩和する）

## 評価

### 評価基準と重み（合計 100%）

研究室アプリでは、**正確性・再現性・目的への適合性・操作効率**を重くし、**視覚的な完成度**を軽くしました。

| 評価基準 | 重み | 重みの理由 |
|---|---|---|
| 操作効率 | 12% | 大量データの入力・比較を毎日行う |
| 学習の容易さ | 8% | 学部生が毎年入れ替わる |
| 情報の理解しやすさ | 10% | 異常値・状態・根拠をひと目で把握する必要がある |
| 視覚的完成度 | 4% | 装飾より情報密度を優先する分類だから |
| アクセシビリティ | 8% | 研究室には多様な利用者がいる。色覚の多様性への対応が必須 |
| 拡張性 | 8% | 新しいソルバー、装置、LCA の係数データベースを追加していく |
| 実装・保守コスト | 8% | 研究室で保守する（高いほど低コスト＝良い、として採点） |
| 目的への適合性 | 12% | 測定・LCA・Math IR の3業務への適合 |
| 正確性（分類固有） | 12% | 単位の取り違えや異常値の見落としを防ぐ |
| 再現性（分類固有） | 12% | 条件・データ・版を追跡して再計算できる |
| 操作速度（分類固有） | 6% | キーボード操作、少ないクリック数 |
| **合計** | **100%** | |

### 採点（1〜5点）と加重合計

主な採点の根拠:
- **案A**: 表の操作は最速です。一方で依存関係が見えないため、再現性は3点にしました（P2 が弱い）。
- **案B**: 図と説明は優れています。一方で大量データの操作に弱く、自由度の高さが記録のばらつきを生みます（X5 に近づく）。そのため、正確性と再現性は3点にしました。
- **案C**: 状態語彙・来歴・版・未適用の表示を骨格に組み込んでいるため、正確性・再現性・適合性は5点にしました。実装コストが重いため、実装・保守コストは2点にしました。

### 採用案: 案C「Pipeline Ledger」（統合型）

**採用理由**
1. 分類固有の3基準（正確性・再現性・目的への適合性。合計 36%）で、全て最高点です。研究室アプリの目的である「計算根拠と使用データの追跡」「変更履歴と再現性」に、最も直接に応えます。
2. 既存リポジトリの Math IR パイプライン（SymPy / SageMath / MATLAB）と LCA 演算子は、段の連鎖として実装されています。その構造をそのまま UI の骨格にできるため、概念のずれが小さくなります。
3. 弱点の実装コストは、部品を段階的に作ることで分散できます（下記）。

**不採用案から取り込む要素**
- **案A から**:
  - 「台帳」タブのデータグリッドの部品を、そのまま使う（列のスキーマ検証、tabular-nums、集計行、数字キーのタグ）
  - 学部生向けの既定画面を、「測定入力」の段のグリッドにする
  - CSV・Excel の往復、保存検索
- **案B から**:
  - 「レポート」の段の出力を、根拠ページ（説明・数式・図・表）として自動で組み立てる
  - 軽い計算は、スライダーで即時に感度分析できるようにする
  - 図の代替の表、論文用の書き出しプリセット、スマートフォンでのコメントレビュー

**段階的な実装の順序（案）**
1. 台帳のグリッドと、スキーマ検証（案A 相当）
2. 段のリストと状態語彙、ジョブモニター
3. 根拠パネル（来歴・版・ハッシュ）
4. レポートの段（案B の部品）
