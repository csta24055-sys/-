# 分類A（大学・研究室内部の研究支援アプリ）設計原則

対象: 研究室内部で使う研究支援アプリ（室内空気質の測定データ管理、建材 LCA 計算、Math IR 計算ジョブの管理）
根拠: 調査台帳 `data/ledger-A-1.json`（6件）と `data/ledger-A-2.json`（6件）の計12件

## 根拠の確認レベル

| 確認レベル | 該当事例 |
|---|---|
| 公式ページ・公式ドキュメントの本文を取得して確認（`fetched_official_page`） | MATLAB, JupyterLab, Origin/OriginPro, LabArchives, Benchling, GraphPad Prism, Weights & Biases, KNIME, ParaView, eLabFTW, Zotero（11件） |
| 検索結果の要約だけで確認（`search_results_only`） | Observable（1件） |

- どの事例も、画面画像は今回のセッションで見ていない。配色・アイコン・余白について台帳に「推測」と書かれた部分は、原則の根拠にしていない。
- 根拠にしたのは文書で確認できた**構造と振る舞い**だけ（ペイン構成、状態表示、履歴、再計算、エクスポートなど）。
- Benchling は製品ページに UI の記述がなかった。機能面（スキーマ、リンク、監査証跡）だけを根拠に使った。

## 共通する優れた設計原則（11項目）

### P1. 「選ぶ・一覧で見る・詳しく見る」を3つの領域に分け、常に同じ位置に置く
左に分類・保存検索・資源、中央に高密度の一覧または作業領域、右に選択中の対象の詳細やプロパティを置く。配置が毎回同じなので、どこを見ればよいか迷わない。大量のデータを、画面を移動せずに見比べられる。
- 根拠: **Zotero**（左=コレクション/タグ/保存検索、中央=項目一覧、右=メタデータ）、**JupyterLab**（左=ファイル・実行中・目次、右=プロパティ・デバッガ）、**ParaView**（左=Pipeline Browser + Properties、中央=ビュー）、**MATLAB**（Workspace / Files / Command Window の常時表示）
- このアプリでの使い方: 測定セッションの一覧（中央）、選択した測定の条件・校正記録・来歴（右）、部屋・装置・プロジェクト・保存検索（左）。

### P2. 計算の依存関係（入力 → 処理 → 結果 → 図）を目に見える形で保ち、元データが変わったら「要再計算」を明示する
結果がどの入力から作られたかを、構造として画面に出す。入力が変わったときは、自動で再計算するか、「古い結果」であることをはっきり示す。
- 根拠: **Origin**（入力データが変わると結果・グラフ・レポートが自動更新され、解析ダイアログを開き直せる）、**GraphPad Prism**（Family 表示で結果を元データの下に入れ子で示す。凍結シートはイタリック）、**KNIME**（処理の流れがノードのグラフとして見える）、**ParaView**（パイプラインのツリーを常時表示）
- このアプリでの使い方: Math IR のパイプライン（数式 → SymPy/SageMath/MATLAB → LCA 演算子 → 図表）を段ごとに表示する。上流の係数を変えたら、下流の段に「要再計算」のバッジを付ける。

### P3. 処理の状態は少数の決まった状態で表し、色・記号・文字の3つで示す
各段・各ジョブ・各記録の状態を「未設定 / 準備完了 / 実行中 / 成功 / 失敗 / 要再計算」などの決まった語彙に絞る。色だけに頼らず、記号と文字ラベルも必ず付ける。状態の意味は研究室ごとに変えられないよう固定する。
- 根拠: **KNIME**（信号機型のステータス表示: 赤=未設定、黄=実行可能、緑=成功、エラー記号=失敗）、**eLabFTW**（ステータスバッジ。ただし色を自由に変えられすぎる点は台帳で「避けるべき」とされている）、**GraphPad Prism**（旧版は赤いグリッドの色だけで読み取り専用を示していた。台帳はこれを反面教師として挙げている）
- このアプリでの使い方: 計算ジョブの一覧と、パイプラインの各段に同じ状態語彙を使う。異常値（例: CO2 > 1000 ppm、ISO クラスの上限超過）にも「色＋記号＋閾値の文字」を付ける。

### P4. 重い計算は利用者が「実行」を決め、まだ適用していない変更を強く見せる
軽い計算は入力と連動して即時に更新する。重い計算は明示的な「実行」ボタンで動かし、未適用の項目をハイライトし、ボタンの状態を変える。この2つを区別する。
- 根拠: **ParaView**（Apply ボタンと Auto Apply の選択。公式ドキュメント自身が「Apply の押し忘れはよくある間違い」と書いている）、**Observable**（リアクティブ再計算で条件変更の影響がすぐ見える。台帳には「重い計算での自動再計算の暴発は避ける」とある）
- このアプリでの使い方: LCA の係数スライダーによる感度分析は即時に更新する。SageMath/MATLAB のジョブ投入は「実行」ボタン＋「未適用 3項目」の表示で行う。

### P5. 全ての記録・計算条件に版の履歴を持たせ、「過去版を表示中」であることを状態バナーで示す
エントリー単位で、誰が・いつ・何を変えたかを残し、任意の版に戻せるようにする。過去版を見ているときは画面上部に固定のバナーを出し、現行版と取り違えないようにする。
- 根拠: **LabArchives**（エントリー単位の履歴と復元。過去版を表示中は青いバナー。older / newer の切替）、**Benchling**（監査証跡）、**eLabFTW**（タイムスタンプ・署名・変更履歴）
- このアプリでの使い方: LCA の計算条件（機能単位、システム境界、排出係数の出典と版）に版番号を付ける。比較のときは「v3 と v5 の差分」を表で並べる。

### P6. 入力は「型と単位を持つ表（スキーマ）」で受け、入力した時点で検証する
自由記述欄だけに数値を書かせない。列に型・単位・許容範囲を定義し、範囲外・単位の取り違え・欠損をセルの上ですぐに示す。最初に「データの型」を選ばせ、その型で使える解析だけを提示する。
- 根拠: **Benchling**（Result schema で列・単位を定義し、チームでデータの一貫性を保つ）、**GraphPad Prism**（データ表の型を最初に選ばせ、適切な解析だけを提示）、**eLabFTW**（カスタムフィールド。台帳には「自由記述欄だけで数値を扱わない」とある）、**LabArchives**（台帳には「数値データを非構造の添付に埋もれさせない」とある）
- このアプリでの使い方: PM2.5 [µg/m³]、CO2 [ppm]、粒子数 [個/m³, ≥0.5 µm] の列を単位付きで固定する。ISO 14644-1 のクラスは粒子数から自動で判定する。単位を取り違えそうな値（例: mg/m³ の入力）は警告する。

### P7. 1行が1試行になる比較表と、表と図での色の一致
試行（run / ジョブ / 測定セッション）を1行にし、条件と結果を列として並べ、列を自由に追加・並べ替え・フィルタできるようにする。試行ごとに固定の色見本を付け、表とグラフで同じ色を使う。表でグループ化したら、図もそのグループで集約する。
- 根拠: **Weights & Biases**（runs table と各パネルの連動、run ごとの色見本、グループ化の図への反映）、**Zotero**（高密度の行リストで列を追加・並べ替え）
- このアプリでの使い方: Math IR ジョブの比較表（solver、精度、実行時間、結果のハッシュ）。建材 LCA の比較表（材料、機能単位、GWP [kg-CO2e]）。

### P8. 研究室の「標準の見方・書き方」をテンプレートで配り、役割ごとに権限を分ける
記録の書式、比較ビュー、エクスポートのプリセットを研究室のテンプレートとして共有し、学生ごとのばらつきを減らす。テンプレートや閾値を管理できるのは教員・管理者に限る。教授（承認・俯瞰）、大学院生（設計・実行）、学部生（定型の入力）で、見える操作を変える。
- 根拠: **LabArchives**（テンプレート。Owner/Admin だけがテンプレートとウィジェットを管理）、**eLabFTW**（テンプレート、役割別のガイドと権限）、**Weights & Biases**（ワークスペースのテンプレート化）、**Benchling**（レビュー済みの結果だけを分析用ビューに出す）
- このアプリでの使い方: 「レビュー済み」状態のデータだけを論文用の図に使えるようにする。学部生には「測定入力テンプレート」だけを既定で表示する。

### P9. GUI の操作を式・スクリプトとして書き出せるようにし、上級者は直接入力もできる二重経路にする
フォームで操作した内容を Math IR や Python のスクリプトとして記録・書き出しできるようにする。上級者は式やコマンドを直接打てる。全ての機能をコマンドパレットからキーボードで呼び出せる。
- 根拠: **ParaView**（GUI 操作をトレースで Python スクリプト化。GUI と同期した Python Shell）、**MATLAB**（Command Window と GUI の併用、Live Script）、**JupyterLab**（コマンドパレット）
- このアプリでの使い方: LCA の条件フォームを保存すると、同じ内容の Math IR（JSON）と SymPy コードを「根拠」タブに表示し、ダウンロードできる。

### P10. 説明・数式・図・表を1つの「計算根拠ページ」にまとめ、指導と報告にそのまま使えるようにする
計算の前提、使った式、入力データ、結果の図表、注記を1つのドキュメントにまとめる。教授のレビューやゼミの報告にそのまま使えるようにする。
- 根拠: **MATLAB**（Live Script でコード・出力・説明を1文書に）、**Observable**（Markdown に図・表・本文を混在）、**KNIME**（ワークフローの説明と注釈）
- このアプリでの使い方: 「CLT 床版 1 m² あたりの GWP」の根拠ページ。式（ΣAᵢ·EFᵢ）、係数の出典 ID、入力表、感度グラフを並べる。

### P11. 開いた形式で取り込み・書き出しをし、元ファイルへのリンクを保つ
CSV / Excel / PDF / JSON などの開いた形式で入出力し、取り込んだ元ファイルへのリンクを保って再インポートできるようにする。書き出しは用途別のプリセット（論文図、ゼミ資料、生データ）で選ぶ。学内のデータを学外に出さない保存先を既定にする。
- 根拠: **Origin**（30以上の形式、元ファイルからの再インポート、Excel なしで取り込み）、**GraphPad Prism**（投稿規定に合わせたエクスポート、CSV/PNG/JSON）、**eLabFTW**（.eln などのオープン形式、自己ホスト）、**Zotero**（取り込み時にメタデータを自動抽出。台帳には「学内保存を選べるようにする」とある）
- このアプリでの使い方: 粒子計数器の CSV を取り込むときに、装置 ID・校正日・測定点を自動で抽出する。PDF レポートには計算条件の版番号とデータのハッシュを印字する。

## 避けるべき設計（7項目）

| # | 避けるべき設計 | 理由 | 根拠の事例 |
|---|---|---|---|
| X1 | **機能を全部、初期画面に出す**（多段のツールストリップ、多数の固定ツールバー、アイコンだけのボタン） | 学部生の学習負荷が大きく、よく使う操作が埋もれる。段階的に開示し、文字ラベルを付ける。 | MATLAB, Origin, ParaView |
| X2 | **実行順を自由にしすぎて、隠れた状態を作る** | セルの実行順や暗黙のカーネル状態に結果が左右されると、再現できない。依存グラフと実行履歴を明示する。 | JupyterLab, Observable |
| X3 | **未適用・古い結果・過去版を目立たない表示のままにする** | 押し忘れや取り違えが起き、誤った値が報告に混ざる。 | ParaView（Apply の押し忘れ）, LabArchives（過去版バナーで解決した例） |
| X4 | **色だけで状態や意味を表す、または色の意味を利用者が自由に変えられる** | 色覚の多様性に対応できず、研究室の中で意味が一定しない。ブランド色と状態色がぶつかることもある。 | GraphPad Prism（旧版の赤グリッド）, eLabFTW（ステータス色の自由設定）, Zotero（色タグ）, KNIME（黄色のブランド色と黄色の状態色） |
| X5 | **数値データを自由記述欄や添付ファイルに埋もれさせる／自由なフォルダ階層だけで整理する** | 集計・比較・検索ができない。整理の仕方が人によってばらつく。 | LabArchives, eLabFTW, GraphPad Prism（逆に固定構造だけで、フォルダもタグもない例） |
| X6 | **詳細ペインに全セクションを既定で展開して詰め込む／初期表示で大量のグラフを自動生成する** | 情報過多で、要点が見えなくなる。折りたたみと要約を既定にする。 | Zotero 7 ベータ, Weights & Biases |
| X7 | **企業向けの重い承認・署名フローを必須にする／外部クラウドへの保存を既定にする** | 研究室では手間が過剰になる。学内規程に合わない。承認は任意の機能にし、学内保存を既定にする。 | Benchling, Weights & Biases, Observable |

## 研究室アプリ固有の補足
- **読み物用の広い余白を、データ入力画面に持ち込まない**（Observable の台帳の注記）。研究室アプリでは、行の高さ 24〜28px、本文 13〜14px を基本にする。読み物（根拠ページ）だけは 15〜16px に広げる。
- **ノード接続だけで全操作をさせない**（KNIME の台帳の注記）。パイプラインは「見る」には優れているが、単純な条件入力はフォームの方が速い。
