対象: 研究支援アプリ、空気清浄度（室内空気質）関連アプリ、建築・環境評価（LCA）系アプリ。
4分類の採用案: A=Pipeline Ledger（研究室内部用）、B=段階的開示3層レイヤー型（国家規模・公共）、C=アウトカム・ハブ（収益追求型の商用）、D=Federated Shell（大企業品質。A〜C に重ねる品質基準）。
既存アプリへの当てはめ方は `application-plan.md` を参照。

## 1. 全体構成

デザインシステムを **2層** に分ける。

```
┌──────────────────────────────────────────────────────────┐
│ テーマ層（分類ごとの値と性格）                               │
│   A: Pipeline Ledger   B: 3層レイヤー型   C: アウトカム・ハブ │
│   └ D: Federated Shell（A〜C のどれにも重ねられる品質基準）    │
├──────────────────────────────────────────────────────────┤
│ 共通の基盤層（全分類で同じもの）                              │
│   トークン命名規則／色・文字・余白・角丸・影・モーションの構造／ │
│   状態設計／アクセシビリティ規則／コンポーネント一覧            │
└──────────────────────────────────────────────────────────┘
```

| 層 | 決めること | 決めないこと |
|---|---|---|
| 基盤層 | トークンの**名前と役割**、状態の種類、アクセシビリティの下限、部品の構造と操作（キーボード・ARIA） | 具体的な色・サイズの値 |
| テーマ層（A/B/C） | トークンの**値**、情報の密度、画面の骨格（ナビゲーションの形）、文言の調子 | トークン名の追加・変更（基盤層の手順を通す） |
| D（重ねる品質基準） | トークンの3層化（基本値 → 意味 → 部品）とバージョン管理、権限・監査・承認の部品、組織ごとのテーマ差し替え、自動検査 | A〜C の性格そのもの（D を重ねても A は研究室向けの高密度のまま） |

### 1.1 トークンの3層（D の基準。基盤層の構造として最初から採用する）

| 層 | 例 | 誰が変えるか |
|---|---|---|
| 基本値（global / primitive） | `teal-700 = #0F6B5C`、`size-4 = 16px` | デザインシステムの管理者だけ |
| 意味（semantic） | `--color-primary`、`--status-good-fg`、`--fs-md` | テーマ層（分類・組織）ごとに値を差し替える |
| 部品（component） | `--button-height`、`--table-row-height` | 部品の担当者。意味トークンだけを参照する |

画面のコードは**意味トークンか部品トークンだけ**を参照する。HEX 値や px 値を直接書かない。現時点の A・B・C の試作（`prototype.html`）は意味トークンの層だけを持っている。D の試作は段階番号の名前（`--space-100`、`--fs-300` など）と意味の名前（`--color-text`、`--status-ok`）を併用している。基本値と部品の層は D を重ねる段階で整える。

## 2. 共通の基盤層

### 2.1 トークン命名規則

**形式: `--{種類}-{役割}[-{変種}][-{状態}]`**（すべて小文字、単語の区切りはハイフン）

| 種類 | 接頭辞 | 例 |
|---|---|---|
| 色 | `--color-` | `--color-primary`、`--color-primary-hover`、`--color-text-muted` |
| 状態色 | `--status-{状態}-fg` / `-bg` | `--status-good-fg`、`--status-good-bg` |
| 図の色 | `--chart-` | `--chart-1`、`--chart-grid`、`--chart-threshold` |
| 書体 | `--font-` | `--font-sans`、`--font-mono` |
| 文字の大きさ | `--fs-` | `--fs-xs`、`--fs-sm`、`--fs-md`、`--fs-lg`、`--fs-xl`、`--fs-2xl` |
| 行高 | `--lh-` | `--lh-tight`、`--lh-body` |
| 余白 | `--space-{番号}` | `--space-1`〜`--space-9` |
| 角丸 | `--radius-` | `--radius-sm`、`--radius-md`、`--radius-lg`、`--radius-pill` |
| 影 | `--shadow-{番号}` | `--shadow-1`、`--shadow-2` |
| モーション | `--dur-` / `--ease` | `--dur-fast`、`--dur-base`、`--ease` |
| 操作対象の大きさ | `--target-` | `--target-min`、`--target-floor` |
| 骨格の寸法 | `--{領域}-w` / `-h` | `--rail-w`、`--header-h`、`--bottomnav-h` |

**現状の不一致と統一の方針**（試作の間で名前が揃っていない箇所）

| 対象 | A の試作 | B の試作 | C の試作 | D の試作 | 統一後 |
|---|---|---|---|---|---|
| 色の接頭辞 | なし（`--bg`、`--text-2`、`--accent`） | `--color-` | `--color-` | `--color-`（組織色は `--brand-accent`） | **`--color-`** に揃える。主色は `--color-primary`（D の `--brand-accent` は組織テーマでの差し替え口として残し、`--color-primary` から参照する） |
| 文字の大きさ | `--fs-xs / sm / md / lg / xl / 2xl` | `--fs-xs / s / m / l / xl / xxl` | `--fs-xs / sm / md / lg / xl / 2xl` | `--fs-100〜600`、`--fs-kpi` | 意味の層は **A・C の名前**に揃える。D の番号の名前は基本値の層の名前として使う |
| 余白 | `--sp-1〜8` | `--space-1〜9` | `--space-1〜7` | `--space-050〜600` | 意味の層は **`--space-{番号}`**。D の番号の名前は基本値の層 |
| 角丸 | `--r-sm / md / lg` | `--radius-s / m / l` | `--radius-sm / md / lg` | `--radius-100 / 200 / 300` | **`--radius-sm / md / lg`** |
| 影 | `--shadow-1 / 2` | `--shadow-1 / 2` | `--shadow-1 / 2` | `--shadow-100 / 300` | **`--shadow-1 / 2`** |
| 標準の速さ | `--dur`（1段のみ） | `--dur-fast`、`--dur` | `--dur-fast`、`--dur-base` | `--dur-fast`、`--dur-base` | **`--dur-fast`、`--dur-base`** |
| 状態色 | `--st-ok`（文字）、`--bg-ok`（背景） | `--status-good-fg / -bg` | `--color-good / -soft` | `--status-ok / -bg` | **`--status-{状態}-fg / -bg`**（B の形）。文字色と背景色を対で持ち、A の5状態や D の「承認待ち」まで同じ形で増やせるため |

統一は §6.4 の廃止手順で行う（旧名を別名として残し、次の大きな版で削除する）。D のトークン原本（Style Dictionary などの JSON）では `color.primary.hover` のように点で区切り、CSS への出力時に `--color-primary-hover` に変換する。D の concepts.md にある `space.050〜space.600` も同じ規則で `--space-*` に対応させる。

### 2.2 色の構造

| 役割のまとまり | 意味トークン | 規則 |
|---|---|---|
| 面 | `--color-bg`、`--color-surface`、`--color-surface-2` | `body` に背景色を明示する |
| 文字 | `--color-text`、`--color-text-muted` | 背景に対して 4.5:1 以上 |
| 境界 | `--color-border`（装飾）、`--color-border-strong`（入力欄など UI 部品の境界） | 部品の境界は 3:1 以上。装飾の線に意味を持たせない |
| 主操作 | `--color-primary`、`--color-primary-hover`、`--color-on-primary` | 主ボタン・リンク・選択状態に使う。状態色と色相を重ねない |
| リンク | `--color-link`、`--color-link-visited` | 本文中のリンクは下線も付ける |
| フォーカス | `--color-focus` | 隣接する色に対して 3:1 以上 |
| 無効 | `--color-disabled-bg`、`--color-disabled-text` | 基準の対象外だが、読める程度の比を確保する |
| 危険 | `--color-danger` | 不可逆な操作のボタンだけに使う |
| 状態 | `--status-{状態}-fg` / `-bg` | §2.7 の状態ごとに対で持つ。**色だけで伝えない**（文言とアイコンの形を必ず併記） |
| 図 | `--chart-1`〜、`--chart-grid`、`--chart-threshold` | 系列は直接ラベルでも区別する。状態色を系列の色に流用しない |
| 分類固有 | §3 を参照（A の過去版バナー、B の層の帯・識別帯・緊急時バナー、C の有料表示、D のスコープバー・組織アクセント） | テーマ層だけで定義し、他の分類では使わない |

### 2.3 文字の構造

- 書体は `--font-sans`（本文）と `--font-mono`（ID・ハッシュ・コード）の2つだけ。
- 数値は `font-variant-numeric: tabular-nums` で桁を揃える（A・C・D の情報源に記載がある）。
- 大きさは6段（`--fs-xs`〜`--fs-2xl`）、行高は2つ（`--lh-tight` は見出し、`--lh-body` は本文）。
- 見出しは h1 → h2 → h3 の順に飛ばさず使い、1画面の h1 は1つにする。
- 値（何 px にするか）はテーマ層で決める。A のように高密度の分類では本文を小さくするが、**最小の文字の大きさは各テーマで明記する**（例: C は 13px を最小とし、それより小さくしない）。

### 2.4 余白の構造

- 4px を最小単位とし、`--space-1` = 4px から番号順に大きくする。
- 部品の内側の余白・部品の間・節の間に、それぞれどの段を使うかをテーマ層で決める（例: C はカード内 24px、カード間 16px、節の間 32px）。

### 2.5 角丸・影の構造

- 角丸は4段（`sm` 入力欄・小部品、`md` ボタン・通知、`lg` カード・ダイアログ、`pill` タグ・切替）。
- 影は2段（`--shadow-1` カード、`--shadow-2` ダイアログとトーストだけ）。影で意味を伝えず、境界線を併用する（Windows のハイコントラスト表示 `forced-colors` で影は消えるため）。

### 2.6 モーションの構造

- `--dur-fast`（ホバー）、`--dur-base`（表示の切替）、`--ease` の3つだけ。
- `prefers-reduced-motion: reduce` のときは、`--dur-*` を 0ms に差し替える（B の試作はこの方法をとっている）。スケルトンの光沢も止める。
- 自動で動き続ける表示、祝福の演出は置かない。

### 2.7 状態設計

状態を3種類に分け、名前を全分類で共通にする。

**(1) 操作の状態**（すべての操作部品）: 既定 / ホバー / 押下 / フォーカス（`:focus-visible`） / 選択 / 無効 / 処理中

**(2) データの状態**（意味の共通化）。各分類の状態は、次の共通の意味のどれかに対応させる。

| 共通の意味 | A（段の状態） | B（区分） | C（部屋の状態） | D（運用の状態） | 形（色以外の手がかり） |
|---|---|---|---|---|---|
| 良い・成功 | 成功（●） | 良好 | 良好 | 良好 | 丸＋チェック |
| 注意 | 準備完了（◐）※ | 注意 | 注意 | 注意 | 三角＋！ |
| 警戒 | — | 警戒 | — | 警戒 | 情報源ごとに異なる |
| 危険・失敗 | 失敗（✕） | 重大 | 要換気 | 警戒 | 八角形＋×（C） |
| 中立・未設定 | 未設定（○） | データなし | — | 中立（`--status-neutral`。試作） | 白丸、斜線（B の図の欠損） |
| 情報 | — | 情報 | （情報通知） | 情報（D の案A） | — |
| 要再計算・古い | 要再計算（↻） | — | — | — | 回転矢印 |
| 承認待ち | —（スマホの「承認」タブはある） | — | — | 承認待ち | — |

※ A の「準備完了」は注意色（`#8A5A00`）を使っているが、意味は注意ではない。A のテーマ層では「準備完了」を独立の状態として扱い、共通の「注意」とは別のトークンにする。

**(3) 画面の状態**（すべての画面）: 読み込み中 / 空 / エラー / 部分的なエラー / オフライン / 権限なし / 過去版を表示中。部品ごとに、この7つの表示を用意する（§5）。

|---|---|---|

## 3. 分類ごとのテーマ層（値と性格の違い）

| 観点 | A: Pipeline Ledger | B: 3層レイヤー型 | C: アウトカム・ハブ | D: Federated Shell |
|---|---|---|---|---|
| 性格 | 「入力 → 処理 → 結果の連鎖の全段に台帳と根拠が付く」 | 「同じページの中で、結論 → 比較 → 根拠の順に深く潜れる」 | 「成果物から始める」「課金理由が見える」「誠実な収益化」 | 「誰が・どの範囲で見ているかを常に明示し、全機能が同じシェルを共有する」 |
| 主な利用者 | 大学院生、教授、学部生 | 一般市民から専門家まで全員 | 有料の利用者（事務所・テナントなど） | 複数組織の全ロール（管理者・責任者・解析者・閲覧者・監査担当） |
| 情報の密度 | 高（段の単位で区切る） | 層ごとに可変（第1層 低 → 第3層 高） | 中（成果物カード中心） | 中〜高（可変。スコープごとに密度を保存） |
| 本文の大きさ | 13px（根拠パネル 12.5px、レポート段 15px） | 16px（第1層の結論 22px、第3層の表 14px） | 16px（表・ボタン 14px、最小 13px） | 14px/20px（表 13px） |
| 骨格 | 左 段のリスト 240px ／ 中央 作業領域 ／ 右 根拠パネル 300px ／ 下 ジョブモニター 160px | 上部 5項目のナビ＋固定の層ナビ。デスクトップは第1層と第2層の2カラム | 左レール 208px＋上部ヘッダー。作成画面は右に文脈パネル 380px | スコープバー 40px＋左レール 64px（展開 232px）＋3列ドリルダウン |
| スマートフォン | 下部タブ3つ（ジョブ / 異常 / 承認）。条件の編集はしない | 下部タブ4つ（ホーム / 地域 / 建物 / 方法）。第2・3層はアコーディオン | 下部タブ4つ（ホーム / データ / レポート / 設定） | 下部ナビ（4項目＋その他）。1列ずつのスタック遷移 |
| 文言の調子 | 専門用語をそのまま使う。来歴（ジョブ ID・版・ハッシュ）を常に書く | 第1層はやさしい日本語。第3層は定義・出典・ライセンスまで書く | 用語を画面・料金表・計測で同じ意味に固定する。価格は税込で触る前に見せる | ロール名・スコープ名を明示する。権限がないときは理由と申請方法を書く |
| 固有の色 | 状態5色、過去版バナー | 層の帯（第2層・第3層）、識別帯、緊急時バナー | 琥珀（有料要素の事前表示専用） | スコープバー、組織アクセント `--brand-accent`、承認待ち |

**分類をまたぐ原則**: 部品の構造（HTML 要素・ARIA・キーボード操作）は基盤層で1つに決め、分類の違いは「密度（行の高さ・列の数）」「サイズ（トークン値）」「文言」「挙動（既定の開閉・確認の段数）」の4点だけで表す。分類ごとに別の部品を作らない。

## 6. 運用ルール

### 6.1 バージョン管理

- トークンと部品をまとめて1つのパッケージとし、**セマンティック・バージョニング**（`主.副.修正`）で管理する。

| 版の上げ方 | 対象となる変更 |
|---|---|
| 主（例: 1.x → 2.0） | トークン名の変更・削除、トークンの意味の変更、部品の操作方法の変更 |
| 副（例: 1.2 → 1.3） | トークン・部品・状態の追加、新しいテーマの追加 |
| 修正（例: 1.2.0 → 1.2.1） | 値の微調整（コントラスト比の基準を満たしたままのもの）、不具合の修正 |

- 変更履歴（`CHANGELOG`）に、変えたトークン・理由・影響する分類を書く。
- 各分類のテーマ層は基盤層の版に従う（例: 「A テーマ 1.3 は基盤 1.3 に対応」）。
- D を重ねる段階では、トークンの原本を JSON（Style Dictionary など）で持ち、CSS・Figma 変数をそこから生成する。手で CSS を直さない。

### 6.2 変更手順

1. **提案**: 変更の理由、対象のトークン・部品、影響する分類を書いて提案する（issue など）。
2. **影響の確認**: 使用箇所を検索し、影響する画面を列挙する。
3. **コントラストの確認**: 色を変える場合は、組み合わせて使う背景すべてについて比を計算し、表に残す（C の design-system.md §2 の形式）。
4. **試作で確認**: 各分類の `prototype.html` に反映し、§6.5 の検証を行う。
5. **レビュー**: 1人以上が確認する。D を重ねている分類では2人とし、権限・監査に関わる部品は監査担当の役割の人も確認する。
6. **公開**: 版を上げ、変更履歴を書く。

### 6.3 命名

- §2.1 の形式に従う。名前は**役割**で付け、見た目で付けない（`--color-primary` はよいが、`--color-teal` は意味トークンには使わない。色名は基本値の層だけで使う）。
- 状態の名前は §2.7 の共通の意味から選ぶ。新しい状態が必要な場合は、共通の意味に対応づけてから追加する。
- 分類固有のトークンには、役割が分かる名前を付ける（例: `--color-layer2`、`--color-identity-bg`）。分類名（`--a-…`）を接頭辞にしない（テーマを差し替えられなくなるため）。

### 6.4 廃止手順

1. 廃止するトークン・部品に「廃止予定」の印を付け、代わりの名前を変更履歴に書く（副の版で行う）。
2. 旧名は新しい名前の**別名**として残す（例: `--fs-m: var(--fs-md);`）。
3. 少なくとも1つの副の版の間、旧名を使っている箇所に開発時の警告を出す（D の原則: 必須の指定が欠けたら警告する考え方と同じ）。
4. 使用箇所が0件になったことを検索で確かめる。
5. 次の主の版で削除する。

§2.1 の名前の統一（A の `--bg` → `--color-bg`、B の `--fs-s` → `--fs-sm`、`--radius-s` → `--radius-sm`、`--dur` → `--dur-base`、C の `--color-good` → `--status-good-fg`、D の `--status-ok` → `--status-good-fg` など）は、この手順で行う。

### 6.5 アクセシビリティ検証の手順（axe-core＋手動確認）

**自動検査（axe-core）**

1. 各分類の試作と、部品の見本画面（C の `#components` 画面など）を対象にする。
2. 検査の対象は WCAG 2.0 / 2.1 / 2.2 の A と AA の規則（axe-core のタグ `wcag2a`、`wcag2aa`、`wcag21aa`、`wcag22aa`）。
3. 画面の状態ごとに検査する（既定・エラー・空・読み込み中・ダイアログを開いた状態・スマホ幅）。状態を変えずに1回だけ検査すると、隠れている部品の違反を見落とす。
4. 合格の基準は「重大（critical）と深刻（serious）の違反が0件」。それ以外の違反は記録し、次の版までに直す。
5. 変更のたびに CI で自動実行する。**CI では公開してよいサンプルデータだけを使う**（研究データを公開リポジトリに入れない方針。`application-plan.md` §9）。

**手動確認**（自動検査で見つけられない項目。毎回の公開前に行う）

| 確認 | 方法 |
|---|---|
| キーボード操作 | マウスを使わず、主要な作業を最後まで行う。フォーカスの順序、フォーカスが固定要素に隠れないこと、ダイアログを閉じたときにフォーカスが戻ることを確かめる |
| 読み上げ | VoiceOver または NVDA で主要な画面を読み、状態の変化（`role=status` / `aria-live`）が読まれることを確かめる |
| 拡大と幅 | 200% 拡大と幅 320px 相当で、横スクロールが出ず、情報が欠けないことを確かめる |
| 色に頼らない | 白黒表示で、状態・系列・閾値が区別できることを確かめる |
| ハイコントラスト | `forced-colors` でボタン・カード・入力欄の枠が見えることを確かめる |
| 動き | `prefers-reduced-motion: reduce` で動きが止まることを確かめる |
| 操作対象の大きさ | 主要な操作が 24px 以上（各テーマの `--target-min` 以上）であることを確かめる |
| 文言 | 誤りの表示が「どこが・なぜ・どう直すか」を含むことを確かめる。B の第1層はやさしい日本語になっていることを確かめる |

- 結果は部品ごと・画面ごとに記録する（日付、版、検査した人、違反と対応）。B の concepts.md にあるように、公共利用（B）ではこの試験結果を「方法と出典」ページで公開する。

### 6.6 D の監査・権限・ログ要件の組み込み方

D の要件は、画面ごとに作り込まず、**基盤層の部品と必須の指定**として組み込む。

| 要件 | 組み込み方 |
|---|---|
| 権限 | 権限の判定を受け取る部品（権限ゲート）を用意する。権限がないときは機能を隠さず、「権限なし（申請方法）」の表示を出す。権限の種類（閲覧者 / 解析者 / 責任者 / 管理者 / 監査担当）は D の基盤で1つに決め、各アプリで増やさない |
| スコープ | スコープバーを最上部に常設し、現在のロールを表示する。スコープを URL に含め、リンクを共有すると同じ範囲・同じ対象が開くようにする |
| 承認 | データを変える部品（フォーム・一括操作）は、「下書き → 申請 → 一次承認 → 最終承認」の段階表示と差分プレビューを部品の機能として持つ。理由の入力を必須にする |
| 監査ログ | データを変える操作は、誰が・いつ・どのスコープで・何を・変更前と変更後・理由、を記録するイベントを出す。部品の必須の指定にし、欠けていたら開発時に警告する。ログの表示は3列目（証跡）に統一する |
| ログに入れないもの | 資格情報・トークン・研究の元データはログにも画面にも出さない（既存の Dropbox OAuth スクリプトの、資格情報をログに出さない設計と同じ方針）。来歴はハッシュで示す |
| 計測との区別 | C の計測（`data-analytics-event`、利用者がオフにできる）と、D の監査ログ（オフにできない）は、別の仕組み・別の名前にする。監査ログを製品改善の分析に流用しない |
| 組織テーマ | 組織が差し替えられるのは `--brand-accent` だけにし、登録時に白地で 4.5:1 以上を自動検査する。状態色は組織テーマで変えない |
| 検査 | 権限・承認・監査の部品には、受け入れ基準（例: 権限がない場合の表示、差分が必ず出ること）を書き、CI で確かめる |

A（研究室内部用）に D を重ねる場合も、最初に入れるのは「トークンの3層化」と「自動のアクセシビリティ検査」であり、承認と監査は研究室の外に結果を出す段階で加える（順序は `application-plan.md` §8）。
