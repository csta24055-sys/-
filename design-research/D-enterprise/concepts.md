# D 分類（大企業品質）— 3 案の UI コンセプトと評価

題材（ダミー）: 『（仮称）EnviroOps Platform』— 複数組織（大学・自治体・建設会社）が共同利用する環境データ基盤。空気質センサー群と LCA 計算ジョブの運用管理、組織 / プロジェクト / ロール、承認フロー、監査ログを扱う。
ダミーの組織名: 北陵大学 環境工学研究室、湊川市 環境政策課、東和建設 技術本部（いずれも架空）。

根拠となる設計原則は `principles.md` の P1〜P12 / X1〜X8 を参照する。

## 比較軸を変えた理由

基本の「実用性重視 / 先進性重視 / 統合型」は、A〜C 分類では「どんな体験を優先するか」の違いになる。しかし D 分類（大企業品質）では、台帳 12 件のどれもが「見た目の方向性」より **「誰が・どの範囲で・どう運用するか」に合わせて情報構造を決める** ことを主題にしていた（P3 画面骨格の標準化、P2 トークンの層、P8 状態の共有、P11 版管理）。そこで比較軸を次のように置き換える。

| 案 | 比較軸（D 分類版） | 元の軸との対応 |
|---|---|---|
| 案A | **単一プロダクト最適型**「Operations Console」— 運用担当者が 1 つの製品の中で最速に作業を終える | 実用性・効率重視 |
| 案B | **ワークスペース・ハブ型**「Insight Workspace」— 組織やプロジェクトごとのワークスペースを、可視化カードで俯瞰する | 先進性・視覚的完成度重視 |
| 案C | **プラットフォーム統合型＋トークン駆動マルチテナント**「Federated Shell」— 共通シェルとスコープ（組織→プロジェクト）を全機能で共有し、組織ブランドはトークンで差し替える | 統合型 |

3 案は色違いではなく、**ナビゲーションの起点（機能 / ワークスペース / スコープ）** と **詳細の開き方（分割パネル / ページ遷移 / 3 列ドリルダウン）** が異なる。

## 案A: 単一プロダクト最適型「Operations Console」

### デザインの基本思想
「運用者の 1 分を削る」。機能（センサー / ジョブ / 承認 / 監査）を左ナビの第一階層に並べ、どの機能でも「高密度テーブル＋右側の分割詳細パネル」という単一の骨格で作業する（P3、P4）。装飾は最小限、状態と数値を主役にする（P7）。

### 想定利用者と主要タスク
- 主利用者: 基盤の運用担当（各組織の運用担当者・プラットフォーム管理者）、LCA 計算ジョブを日常的に回す解析者
- 主要タスク: 異常センサーの一次切り分け、失敗ジョブの再実行、承認待ちの一括処理、監査ログの条件検索と CSV 出力

### 代表的な画面構成
- 上部グローバルバー（高さ 48px）: 製品名、組織スイッチャ、グローバル検索（`/` キー）、通知、ユーザー
- 左ナビ（幅 232px、折り畳み 56px）: 概要 / センサー / LCA ジョブ / 承認 / 監査ログ / 組織と権限 / 設定
- 本文: ページ見出し＋件数 → フィルタバー（トークン化されたフィルタ、URL に保持、P8）→ データテーブル → ページネーション
- 右分割パネル（幅 400px、開閉可）: 行選択時に詳細・時系列ミニグラフ・関連承認・監査イベント

### ナビゲーション
機能起点の 2 階層。組織は「フィルタの 1 条件」として扱う（組織スイッチャで既定値を変える）。キーボード: `g s` でセンサー、`g j` でジョブ、`j / k` で行移動、`Enter` で詳細パネル、`x` で選択。

### 配色・フォント・余白
- 背景 `#F5F6F8` / 面 `#FFFFFF` / 文字 `#1B1F24` / 補助文字 `#4A5260` / 境界 `#D3D8DF`
- アクセント `#0B5CAD`（白地で約 6.6:1）
- 状態: 良好 `#1E7A3C` / 注意 `#8A5A00` / 警戒 `#B42318` / 情報 `#0B5CAD`（いずれも白地で 4.5:1 以上。色だけでなくアイコンと文言を併記）
- フォント: `system-ui, "Hiragino Sans", "Noto Sans JP", "Yu Gothic UI", sans-serif`、本文 13px/20px、表 13px、数値は `font-variant-numeric: tabular-nums`、ID は等幅
- 余白: 4px 基本単位（4/8/12/16/24）、テーブル行高 32px（既定）を 24/32/40 の 3 段階で切替

### 情報表示の密度
高。1 画面に 25〜40 行。詳細パネルを開いても一覧を残す。

### グラフ・表・入力フォーム
- 表: 列の表示 / 並び替えを利用者が保存、3 状態ソート、選択時に一括操作バー（最大 5 操作＋その他）、固定ヘッダー、仮想スクロール
- グラフ: 詳細パネル内のスパークライン（直近 24 時間）と閾値線。大きなグラフは別タブ
- フォーム: 右パネル内のインライン編集、項目単位の検証、未保存変更の離脱警告（P6）

### デスクトップとスマートフォンの違い
デスクトップが主。スマートフォンは「当番対応用の縮退版」: 下部タブ（アラート / 承認 / 検索）、テーブルはリスト行に変換、一括操作は不可、承認と確認だけを許可。

### アクセシビリティ
すべての操作をキーボードで完結、フォーカスリング 2px `#0B5CAD`＋2px オフセット、テーブルは `aria-sort` / `aria-selected`、行高の大きい設定と 200% 拡大で崩れない設計。状態は色＋形＋文言。

### 採用技術と実装難易度
React（または Web Components）＋ヘッドレス UI（React Aria 等）＋仮想スクロール（TanStack Table / Virtual）、トークンは CSS カスタムプロパティ。難易度: **中**（骨格が 1 種類のため部品数は少ない）。

### メリット / デメリット
- メリット: 操作効率が最も高い。骨格が 1 種類なので一貫性と保守性が高い。キーボード操作と相性が良い。
- デメリット: 非専門の閲覧者（自治体の管理職、研究室の学生）には密度が高く入りにくい。組織をまたぐ横断的な見方（組織ごとの状況比較）が弱い。組織ごとのブランド表現の余地がない。

## 案B: ワークスペース・ハブ型「Insight Workspace」

### デザインの基本思想
「まず状況を見て、気になったところに入る」。組織またはプロジェクトごとの **ワークスペース** を入口にし、カード型の可視化ダッシュボードで俯瞰する。カードは利用者が並べ替え・サイズ変更できる（Cloudscape の設定型ダッシュボード、P3）。視覚的完成度を高め、報告・説明の場面でもそのまま使える画面にする。

### 想定利用者と主要タスク
- 主利用者: 自治体の担当課・管理職、研究室の PI、建設会社のプロジェクト責任者（意思決定者・閲覧者）
- 主要タスク: 施設・地区ごとの空気質の把握、LCA 結果の比較と共有、月次報告のエクスポート、承認の判断

### 代表的な画面構成
- 上部ヘッダー（高さ 64px、濃色）: ワークスペース切替（大きなドロップダウン）、上部タブ（概要 / センサー / LCA / 承認 / レポート）、検索、ユーザー
- 本文: KPI カード 4 枚 → 地図（センサー配置）と時系列の大カード → LCA シナリオ比較カード → 最近の活動
- 詳細は **ページ遷移** で開く（パンくずで戻る）

### ナビゲーション
ワークスペース起点。組織 → ワークスペースを選んでから機能タブに入る。組織横断の比較は「比較ワークスペース」を作成して行う。

### 配色・フォント・余白
- 背景 `#F3F4F7` / 面 `#FFFFFF` / ヘッダー `#14213D`（白文字で約 16:1）/ 文字 `#172033` / 補助文字 `#4D5870`
- アクセント `#3047C9`（白地で約 7.3:1）/ 第 2 アクセント `#00695C`
- データ系列: `#3047C9` `#00695C` `#A04A00` `#7B3FA0`（いずれも白地で 4.5:1 以上、系列はマーカー形状も変える）
- フォント: 同じ日本語スタックで見出しを大きく（KPI 数値 28px/36px、見出し 20px）、本文 15px/24px
- 余白: 8px 基本単位（8/16/24/32）、カード角丸 12px、カード間 24px

### 情報表示の密度
低〜中。1 画面にカード 6〜8 枚。表は 1 カード 5〜10 行。

### グラフ・表・入力フォーム
- グラフ: 主役。時系列の帯グラフ、地図上のセンサー、LCA の段階別積み上げ棒（製造 / 輸送 / 施工 / 運用 / 解体）。各グラフに「表で見る」切替を必須にする
- 表: カード内の簡易表、全件は詳細ページ
- フォーム: ステップ形式のウィザード（LCA シナリオ作成：対象 → 材料 → 係数 → 確認）

### デスクトップとスマートフォンの違い
スマートフォンでもほぼ同じ体験を提供: カードを 1 列に積む、上部タブを下部ナビバー（5 項目）に移す、地図は全画面切替。閲覧中心のため差が小さい。

### アクセシビリティ
グラフごとに代替表とテキスト要約、系列は色＋形状、カードは見出し付きの `section`。ただしカードの自由配置はキーボードでの並べ替え操作（移動モード）を別途用意する必要があり、実装を誤るとアクセシビリティが下がりやすい。

### 採用技術と実装難易度
React ＋可視化ライブラリ（Vega-Lite / ECharts 等）＋地図（MapLibre）＋グリッドレイアウト。難易度: **中〜高**（可視化・地図・カード配置の部品が多い）。

### メリット / デメリット
- メリット: 閲覧者・意思決定者にとって最も分かりやすく、視覚的完成度が高い。報告場面にそのまま使える。スマートフォンとの差が小さい。
- デメリット: 大量データの一括処理が遅い（ページ遷移が多い）。ワークスペースごとに見た目と構成が自由に変わるため、多組織運用での一貫性が崩れやすい（X3、X8 のリスク）。権限・承認・監査のような運用機能がカードの「おまけ」になりやすい。

## 案C: プラットフォーム統合型＋トークン駆動マルチテナント「Federated Shell」（統合型）

### デザインの基本思想
「誰が・どの範囲で見ているかを常に明示し、全機能が同じシェルを共有する」。画面上部に **スコープバー**（組織 › プロジェクト › 環境）を常設し、全機能・全データがこのスコープで絞られる。詳細は **3 列ドリルダウン**（一覧 → 詳細 → 証跡 / 承認）で開き、ページ遷移なしに監査情報まで辿れる（Fiori の FCL 原則、P3、P12）。組織ブランドはアクセント系トークンだけを差し替え、状態色・余白・文字は全組織共通（P1、P2、X3）。案A の高密度テーブルと、案B の概要ダッシュボードを「スコープのホーム」として取り込む。

### 想定利用者と主要タスク
- 主利用者: 3 種類の組織の全ロール（組織管理者 / プロジェクト責任者 / 解析者 / 閲覧者 / 監査担当）
- 主要タスク: スコープを切り替えての状況把握、センサー校正値変更や LCA 結果公開の申請→承認、承認キューの処理、監査ログの追跡、組織横断の共同プロジェクト運用

### 代表的な画面構成
- スコープバー（高さ 40px、濃色 `#0F2A3D`）: 組織 › プロジェクト › 環境（本番 / 検証）のパンくず型切替、現在のロール表示（例「解析者」）、コマンドパレット（`Ctrl/⌘ + K`）
- 左レール（幅 64px、ホバー / ピン留めで 232px）: ホーム / センサー / LCA ジョブ / 承認 / 監査 / 管理
- 本文: 3 列ドリルダウン
  - 列 1: 一覧（案A と同じ高密度テーブル、密度 3 段階）
  - 列 2: 詳細（概要・時系列・設定値）
  - 列 3: 証跡（変更履歴・承認の経過・監査イベント・値の出所）
- 承認は「受信箱」型: 申請 → 一次承認 → 最終承認の段階を横並びのステップで表示し、差分（変更前 / 変更後）を必ず提示

### ナビゲーション
スコープ起点 → 機能 → 対象の 3 段。スコープは URL に含める（`/org/hokuryo-univ/proj/campus-aq/sensors/AQ-0142`）ので、リンク共有で同じ範囲・同じ対象を開ける（P8）。権限のない機能はナビから消さず「権限なし（申請方法）」の画面を出す（Ant の Exception、P5）。

### 配色・フォント・余白
- 共通: 背景 `#F6F7F9` / 面 `#FFFFFF` / 文字 `#16191D` / 補助文字 `#4B5563`（白地で約 7.6:1）/ 境界 `#D1D5DB` / スコープバー `#0F2A3D`
- 状態（全組織共通・固定）: 良好 `#1E7A3C` / 注意 `#8A5A00` / 警戒 `#B42318` / 承認待ち `#5B3FA0`
- 組織アクセント（トークン `--brand-accent` のみ差し替え、白地で 4.5:1 以上を検証して登録）: 北陵大学 `#1D5FA8` / 湊川市 `#1F6F4A` / 東和建設 `#8A4B0F`
- フォント: 案A と同じスタック、本文 14px/20px、表 13px、見出し 16/20/24px の 3 段のみ
- 余白: 4px 基本単位、段階トークン `space.050〜space.600`、列間 1px 境界＋16px 内余白

### 情報表示の密度
中〜高（可変）。列 1 だけ開いているときは案A と同等、3 列すべて開くと各列が要約表示になる。利用者がスコープごとに密度設定を保存できる。

### グラフ・表・入力フォーム
- 表: 案A と同じ仕様（3 状態ソート、一括操作バー、保存ビュー）
- グラフ: 列 2 に中サイズの時系列（閾値帯・欠測区間を明示）。スコープのホームに案B 由来の KPI カード（固定配置、自由配置は不可で一貫性を保つ）
- フォーム: 変更はすべて「下書き → 申請」。申請時に差分プレビュー、理由の入力必須、承認者の自動提示。高リスク変更は対象 ID の入力で確認（P6）

### デスクトップとスマートフォンの違い
- デスクトップ: 3 列ドリルダウン
- タブレット: 2 列（列 3 はシート表示）
- スマートフォン: 1 列ずつのスタック遷移（一覧 → 詳細 → 証跡を戻るボタンで移動）、スコープバーは上部の 1 行要約（タップで切替シート）、左レールは下部ナビバー（4 項目＋その他）。承認は差分を確認したうえでスマートフォンからも可能

### アクセシビリティ
ランドマーク（スコープバー=`banner`、レール=`navigation`、各列=`region` に見出し）、列間を `F6` で移動、コマンドパレットで全機能に到達、組織アクセントの登録時にコントラスト自動検査、状態は色＋アイコン＋文言、時系列グラフに代替表。

### 採用技術と実装難易度
React ＋ヘッドレス UI、トークンは 3 層（global / semantic / component）を Style Dictionary 等で生成し、組織テーマは JSON で配布。ルーティングにスコープを埋め込み、権限は ABAC/RBAC を UI 側でも参照。難易度: **高**（スコープ・権限・3 列状態管理の設計が必要）。ただし骨格が統一されているため、機能追加時の限界コストは低い。

### メリット / デメリット
- メリット: 多組織・多ロールの運用に最も適合。承認・監査が主要導線に入っていて、セキュリティ設計と運用性が高い。組織ごとのブランドを許しつつ一貫性を崩さない。機能追加はシェルに載せるだけで済む。
- デメリット: 初期の設計・実装コストが最も高い。スコープの概念を初回利用者に教える必要がある（学習コスト）。3 列は 1280px 未満で窮屈になるため、列の自動畳み込みの調整が必要。

## 評価

### 評価基準と重み（D 分類版、合計 100%）

D 分類は「長期運用・多組織・多ロール」が前提のため、アクセシビリティと操作効率に加え、分類固有の 一貫性・運用性・セキュリティ設計 に合計 22% を配分した。視覚的完成度は「成熟度」の一部として評価するが、高級感の演出は目的ではないため重みを抑えた。

| 評価基準 | 重み | 重みの理由 |
|---|---:|---|
| 操作効率 | 12% | 運用担当者の日常業務の大半を占める |
| 学習の容易さ | 8% | 複数組織の新規参加者が継続的に発生する |
| 情報の理解しやすさ | 10% | 誤読が承認・公開ミスに直結する |
| 視覚的完成度 | 8% | 成熟度として必要だが主目的ではない |
| アクセシビリティ | 12% | 公共機関（自治体）を含む利用者への責務 |
| 拡張性 | 10% | 組織・機能・センサー種別が増え続ける |
| 実装・保守コスト（低いほど高得点） | 8% | 大学主体の開発体制で長期保守する |
| 目的への適合性 | 10% | 共同利用基盤としての要件充足 |
| 一貫性（分類固有） | 8% | 多チーム・多組織で同じ操作体系を保てるか |
| 運用性（分類固有） | 8% | 障害時の縮退、当番対応、設定の配布 |
| セキュリティ設計（分類固有） | 6% | スコープ明示、権限、承認、監査の UI 表現 |
| **合計** | **100%** | |

採点の主な理由:

### 採用案: 案C「Federated Shell」（プラットフォーム統合型＋トークン駆動マルチテナント）

採用理由:
1. 『EnviroOps Platform』の本質は「大学・自治体・建設会社が同じ基盤を、異なる権限で共有する」ことであり、スコープ（組織 › プロジェクト › 環境）を全画面で明示する案C だけが、誤操作（別組織のデータを承認する等）を構造的に防げる（セキュリティ設計 5）。
2. 承認と監査が「3 列目の証跡」として主要導線に入っており、値の出所（P12）・差分承認（P6）を後付けでなく骨格で保証できる。
3. 組織ブランドをアクセントトークンだけに限定することで、各組織の受け入れやすさと、状態色の全組織共通（X3 の回避）を両立する。
4. 機能追加はシェルと 3 列の骨格に載せるだけで済み、長期運用の限界コストが低い（P3、P11）。

### 不採用案から取り込む要素
