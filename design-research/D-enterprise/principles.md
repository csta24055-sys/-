# D 分類（大企業品質）— 共通する優れた設計原則と避けるべき設計

対象台帳: `data/ledger-D-1.json`（D-1-1〜D-1-6）、`data/ledger-D-2.json`（D-2-1〜D-2-6）の計 12 件。

## 確認レベルについて（正直な記録）

- 公式ページを本セッションで取得: 10 件（Fluent 2 / Apple HIG（Liquid Glass 技術概要のみ本文取得、HIG 本文は JS 描画で取得不可）/ Material 3（Android Developers 版）/ Atlassian / Carbon / Polaris / Primer / Spectrum / Ant Design / Cloudscape）
- 検索結果のみ: 2 件（SAP Fiori、Salesforce SLDS 2）。この 2 件を根拠にした項目は「検索結果ベース」と明記する。
- 12 件とも **製品画面の見た目そのものは確認していない**。書体・具体的配色・角丸などの視覚的特徴は台帳でも「事前知識・未確認」とされているため、本書では原則の根拠に使わず、ガイドラインの記述（構造・ルール・数値）だけを根拠にした。
- 以下の原則は事例の紹介ではなく、複数事例に共通して現れた「判断のルール」を抽出し、EnviroOps Platform（複数組織が共同利用する環境データ基盤、仮称）に当てはめた形で書いている。

## 共通する優れた設計原則（12 項目）

### P1. 色・余白・文字は「値」ではなく「役割」で定義し、トークンを唯一の情報源にする
画面のコードに `#0B5CAD` や `13px` を直接書かない。`color.text.subtle`、`space.200`、`status.danger.bg` のように用途名で定義し、テーマ変更・ダーク化・組織ごとの差し替えをトークンの差し替えだけで済ませる。背景色の上に置く文字色はペア（on-X）で定義し、コントラストを構造的に保証する。
- 根拠: Atlassian Design System（トークンを唯一の情報源、トークンピッカー）、Google Material Design 3（色ロールと on-X ペア）、Shopify Polaris（tone で意味、color で強度を指定）、GitHub Primer（Primitives とトークン命名規則）、Salesforce SLDS 2（グローバルスタイリングフック。検索結果ベース）
- EnviroOps への適用: 空気質の判定色（良好/注意/警戒）や承認状態は semantic トークンで固定し、組織ブランドが変わっても変えない。

### P2. トークンは層（グローバル / セマンティック / コンポーネント）で分け、移行と自動検査を最初から用意する
長期運用では「新旧が併存する期間」が必ず生じる。層ごとに名前空間を分け、旧値からの移行ガイドと Lint（ハードコード値の検出）を設計システムの一部として最初から持つ。
- 根拠: Salesforce SLDS 2（`--slds-g-` 接頭辞、SLDS 1 へのフォールバック値併記、Linter / Validator。検索結果ベース）、Atlassian Design System（ハードコード値からの移行ガイド）、GitHub Primer（CSS 変数への移行ガイド）、Microsoft Fluent 2（同じトークン名をプラットフォーム別の単位 px/pt/dp で読み替え）

### P3. 個々の画面より先に「画面骨格（フロアプラン / アプリシェル）」を標準化する
新しい機能を作るたびに画面構成を考えない。「一覧 → 詳細」「一覧＋分割パネル」「ダッシュボード」「結果 / 例外」など少数の骨格を決め、全機能をそこに載せる。利用者は機能が増えても学び直さずに済む。
- 根拠: SAP Fiori（フロアプラン、Flexible Column Layout による最大 3 列のドリルダウン。検索結果ベース）、IBM Carbon（UI shell: header / left panel / right panel）、AWS Cloudscape（Service navigation、Table / Card / Split view、Details page、Service dashboard）、Ant Design（Form / Workbench / List / Result / Exception のテンプレート）
- EnviroOps への適用: センサー一覧、LCA ジョブ一覧、承認キュー、監査ログはすべて同じ「一覧＋詳細パネル」骨格に載せる。

### P4. 情報密度は利用者が選べる段階値にし、周辺要素の寸法を連動させる
業務データ画面では「余白が多い＝上質」ではない。行高を段階化（例: 24/32/40/48px）し、ツールバー・ページネーションの高さもそれに連動させる。密度は利用者設定として保存する。
- 根拠: IBM Carbon（データテーブル 5 段階行高と周辺要素の連動）、AWS Cloudscape（Density settings パターン）、Microsoft Fluent 2（密度の専用ガイドがない点が弱点として台帳に記録＝反面根拠）

### P5. 空・読み込み・部分障害・完了・失敗・権限なしを「一級の画面状態」として設計する
正常系の画面だけを作らない。空状態は「データがまだ無い」と「フィルタに一致しない」を区別する。読み込みが続く場合はスピナーでなくスケルトンにする。外部サービスの一部停止時は、画面全体を落とさず該当部分だけを縮退表示する。
- 根拠: GitHub Primer（degraded experiences、empty states、loading、saving）、IBM Carbon（スケルトン、空状態・読み取り専用・無効状態のパターン）、Ant Design（Result / Exception テンプレート：完了・失敗・権限なし）、AWS Cloudscape（空状態の 2 種類の区別、読み込みと再読み込み）
- EnviroOps への適用: 数学エンジン（SymPy / SageMath / MATLAB）の一つが停止しても、LCA ジョブ一覧は表示し、該当ジョブにだけ「エンジン停止中・再試行待ち」を出す。

### P6. 確認ダイアログは操作のリスクに比例させ、未保存変更は必ず守る
すべての操作に同じ「よろしいですか？」を出さない。低リスクは 1 クリック＋取り消し、作り直しにくいものは簡易確認、重大なもの（組織削除、校正値の一括変更）は対象名の入力など追加確認にする。編集中の離脱は警告する。
- 根拠: AWS Cloudscape（削除の 3 段階、unsaved changes）、SAP Fiori（FCL / Dynamic Page でのデータ損失メッセージ必須。検索結果ベース）、Shopify Polaris（name と defaultValue による dirty-state 追跡）

### P7. 1 画面で強い注意を引く要素は 1 つに絞り、操作系は内容より控えめにする
主要操作（例:「承認する」「計算を実行」）を 1 つだけ高注意にし、ナビゲーションの選択状態や補助操作はそれと競わせない。装飾ではなく、内容（データ）を主役にする。
- 根拠: Adobe Spectrum（Attention hierarchy：1 ページに高注意の要素は 1 つ）、Apple HIG / Liquid Glass 技術概要（コンテンツが主役、操作系の色は控えめ）、Google Material Design 3（強調度別のボタン階層）

### P8. 画面の状態（フィルタ・並び順・選択中の組織 / プロジェクト）は URL と保存ビューで共有できるようにする
多人数・多組織運用では「この条件で見て」と他人に渡せることが重要。フィルタを URL に保持し、名前付きの保存ビューを提供する。CRUD・検索・フィルタは操作単位で標準パターン化する。
- 根拠: AWS Cloudscape（フィルタの URL 保持、保存済みフィルタセット）、GitHub Primer（Scenario Patterns：copy / create / edit / delete / filter / search / view）

### P9. アクセシビリティは「後から検査」ではなく、部品と開発工程に埋め込む
ラベル・エラー文言・フォーカス管理・キーボード操作を部品側が持ち、必須プロパティが欠けたら開発時に警告する。設計段階でフォーカス順とコントラストを検証する。タッチターゲットの最小寸法を数値で決める。
- 根拠: Shopify Polaris（必須プロパティ欠落時の警告、セマンティック HTML・ARIA・フォーカス管理を部品が保持）、Microsoft Fluent 2（A11y Focus Order / Color Contrast Checker プラグイン、タッチターゲット 44/48）、Atlassian Design System（ドキュメント自体のスキップリンク・テーマ切替）、Google Material Design 3（on-X ペアによるコントラスト担保）

### P10. ナビゲーションは画面幅に応じて段階的に切り替え、部品単位でもレスポンシブにする
同じ情報構造を保ったまま、狭い画面では下部バー、中間ではレール、広い画面では常設サイドナビに切り替える。多列表示は狭い画面で常時出さない。
- 根拠: Google Material Design 3（NavigationBar / Rail / Drawer の切替）、Microsoft Fluent 2（6 段階ブレークポイント、reposition / resize / reflow）、Shopify Polaris（コンテナクエリ）、SAP Fiori（狭い画面で 3 列を常時表示しない。検索結果ベース）

### P11. 設計システム自体にバージョンと成熟度を付け、変更を追跡可能にする
部品に alpha / beta / stable を表示し、ガイドラインの変更履歴を公開する。どの画面がどの版に準拠しているかを追えるようにする。ベータ部品に基幹機能を依存させない。
- 根拠: GitHub Primer（component status）、Adobe Spectrum（ベータの明示、What's new）、SAP Fiori（バージョン付きガイドラインと What's New。検索結果ベース）、Apple HIG / Liquid Glass 技術概要（全面刷新を求めない段階的移行）

### P12. 数値・単位・日時の表記と「値の出所」を規則化する
CO2 換算値、PM2.5 濃度、日時（相対 / 絶対）、桁区切りの表記を全画面で統一する。自動推定値・AI 生成値・手入力値は出所ラベルで区別する。
- 根拠: Ant Design（Data Format ルール）、AWS Cloudscape（タイムスタンプの相対 / 絶対の指針）、IBM Carbon（AI 生成内容への AI ラベル）
- EnviroOps への適用: LCA 結果の各値に「計算エンジン・係数の出典 DB・版」を付け、監査ログから辿れるようにする。

## 避けるべき設計（8 項目）

### X1. 他社のブランド資産・画面構成をそのまま模倣する
特定企業の書体、配色、アイコンセット、ヘッダー構成を流用すると、その企業の製品に見え、権利面でも問題になる。台帳 12 件すべての avoid 欄に共通して記録されている。
- 根拠: 全 12 件（特に Fluent 2、Carbon、Fiori、Primer、Spectrum の avoid 欄）

### X2. 半透明素材・大胆な形状や動きをデータ密度の高い画面に持ち込む
背景によって可読性が変わる素材や、表現力重視の形状・モーションは、数値表や判定色の読み取りを妨げる。
- 根拠: Apple HIG / Liquid Glass（データ画面への半透明素材の多用、ガラスの重ね掛けを避ける）、Google Material Design 3（M3 Expressive をデータ密度の高い画面に持ち込まない）

### X3. 状態色の意味を、テーマや壁紙・組織ブランドに連動させて変えてしまう
「警戒＝赤系」などの意味色が組織ごと・端末ごとに変わると、多組織運用で誤読が起きる。
- 根拠: Google Material Design 3（業務アプリでの動的カラーは状態色の一貫性を壊す）、SAP Fiori（セマンティックカラーは状態表示だけに使う。検索結果ベース）

### X4. データテーブルをスプレッドシートの代わりにする、入れ子にする、狭い場所に押し込む
表は「閲覧・選択・一括操作」の部品であり、表計算の代替ではない。LCA の大規模な係数編集などは専用エディタを別に設計する。
- 根拠: IBM Carbon（公式がスプレッドシート代替・入れ子・狭いコンテナ配置を非推奨）

### X5. トースト通知・モーダルを多用する
重要な結果がすぐ消える通知で伝わる、作業がモーダルで中断される、という状態を避ける。結果はページ内に残し、モーダルは高リスク確認に限定する。
- 根拠: Ant Design（トースト・モーダルの多用を避ける、Stay on the Page）、AWS Cloudscape（リスクに応じた確認の段階化）

### X6. 補助パネルや多列表示を常時出して主作業の領域を圧迫する
右パネル・詳細列は「必要なときに開く」ものにする。狭い画面では列を畳む。
- 根拠: AWS Cloudscape（補助パネルの多用を避ける）、SAP Fiori（狭い画面で 3 列を常時表示しない。検索結果ベース）

### X7. 移行途中・ベータ段階の基盤に長期運用の機能を依存させる
グローバル層とコンポーネント層でサポート状況が食い違う、ベータ部品が基幹画面に入っている、という状態は保守コストを長期に押し上げる。
- 根拠: Salesforce SLDS 2（コンポーネント層フックが未サポートの期間。検索結果ベース）、Adobe Spectrum（実装がベータで一部ガイダンスが「今後公開」）

### X8. 抽象的な「価値」だけを掲げ、具体的な判断基準（数値・ルール）に落とさない
「シンプルに」「分かりやすく」だけでは多チーム開発で解釈が割れる。行高・余白・確認段階・表記ルールを数値と条件で書く。
- 根拠: Ant Design（価値の記述の抽象度が高い点が弱点として記録）、Microsoft Fluent 2（具体的な数値ルールが強みとして記録＝対比）
