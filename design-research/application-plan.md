# 成果物6: 既存アプリへの適用計画

対象: `existing-projects-analysis.md` で調べた既存プロジェクトと、まだ見つかっていないアプリ。
前提: 4分類の採用案は A=Pipeline Ledger、B=段階的開示3層レイヤー型、C=アウトカム・ハブ、D=Federated Shell（いずれも統合型の案C）。D は単独の分類ではなく、A〜C に重ねる品質基準として扱う。
デザインの値（色・文字・余白など）は `recommended-design-system.md` と各分類の `design-system.md` に従う。

> 根拠の範囲: 中身を読んだのはリポジトリ `csta24055-sys/-` だけである。他の4リポジトリは名前と説明しか分かっていない。空気質アプリと LCA アプリ本体は見つかっていない。この計画のうち、それらに関する部分は推測であり、中身を確認した時点で見直す。

---

## 0. 全体方針（全プロジェクト共通）

1. **本番 UI と計算コードには手を入れない。** UI は新しいファイル・新しいディレクトリに作る。既存の Python、MATLAB、ワークフロー（`.github/workflows/*.yml`）は読み取り専用の部品として使う。
2. **読むだけの UI から始める。** 最初は、既存の成果物 JSON を読み込んで表示するだけの画面を作る。計算を UI から起動する機能は、第2段階以降に回す。
3. **ローカル完結を既定にする。** 研究データは利用者の手元から外に出さない（§9 を参照）。
4. **D の品質基準は段階的に重ねる。** 最初からすべてを満たそうとしない。商用化・公共利用に進む時点で、§8 の順に追加する。
5. **値はトークン経由で使う。** 画面に HEX 値や px 値を直接書かない。分類を後から変えても、テーマ層の差し替えだけで済むようにする。

### 0.1 本番 UI を変えないための共通手順

| 手順 | 内容 |
|---|---|
| 1. 置き場所を分ける | 新しい UI は `ui/`（例: `ui/math-ir-viewer/`、`ui/lca-playground/`）に作る。既存の `math_interop_v0/`、`math_tools_v2/`、`scripts/` にはファイルを追加しない |
| 2. 依存の向きを一方向にする | UI が既存コードを `import` するか、既存コードの出力 JSON を読むだけにする。既存コードが UI を参照することはない |
| 3. ブランチを分ける | `ui/<名前>` のような作業ブランチで作り、既存ワークフローの CI がすべて成功したままであることを確かめてから統合する |
| 4. CI を分ける | UI 用の検査（axe-core、表示確認）は新しいワークフロー（例: `ui-check.yml`）に書く。既存のワークフローの `on:` や手順は変えない |
| 5. 既存の出力形式を契約として固定する | UI が読む JSON の項目（例: `result_sha256`、`verification_level`）を `ui/<名前>/CONTRACT.md` に書き出し、形式が変わったら UI 側の検査が落ちるようにする |
| 6. 取り消せる形で入れる | UI のディレクトリを消すだけで元の状態に戻ることを、統合前に確かめる |

## 6. まだ見つかっていない空気質（室内空気質）アプリ

リポジトリ全体で「空気」「IAQ」「PM2.5」「換気」を検索したが、該当するものはなかった。**用途によって分類が分かれるので、用途を確かめてから決める。**

| 用途 | 分類と採用案 | 最初に作る画面・部品 |
|---|---|---|
| 研究室で計測データを集めて可視化する | **A / Pipeline Ledger**。段は「取り込み → 検証（校正・欠測） → 集計 → 図表」 | センサーの来歴と校正記録を示す根拠パネル、測定値の台帳（グリッド） |
| 学校・公共施設の空気質を広く見せる | **B＋D / 3層レイヤー型**（D は Federated Shell の権限・監査の考え方を運用側に使う） | 第1層の結論カード（区分・数値・意味・推奨行動）、閾値の根拠を示す第3層 |
| 一般家庭・テナント向けの監視サービス | **C＋D / アウトカム・ハブ** | 部屋ごとの状態（色＋アイコン形状＋文言＋数値）、使用量メーター、通知設定。C の `prototype.html` が見本になる |

- 活かせる既存資産: 「厳密値・単位・来歴ハッシュ・安全側の拒否」という Math IR の設計思想を、測定値の信頼性表示（どのセンサーの、いつの、校正済みの値か）に使える。
- 足りないもの: 現行の単位リストに濃度系の単位（ppm、µg/m³ など）はない。追加するなら Math IR 側の変更となり、変更コストは**中**（推測）。
- 在室推定などは個人情報になりうる。C＋D の場合は、計測の同意とデータ保持期間を最初の画面設計に含める。

## 8. 商用化・公共利用に進む場合に D の品質基準を重ねる順序

D（Federated Shell）の基準は、利用者が増える順・失敗したときの影響が大きい順に重ねる。

| 順 | 重ねる基準 | 理由 | 必要になる時点 |
|---|---|---|---|
| 1 | **トークンの3層化**（基本値 → 意味 → 部品）とトークンのバージョン管理 | 後の段階（テーマ、ホワイトラベル、ダーク）をすべてトークンの差し替えで済ませるための土台。最初に入れるほど安い | 研究室の外の人が1人でも使う前 |
| 2 | **アクセシビリティの自動検査を CI に入れる**（axe-core）と、部品ごとの受け入れ基準 | 公共利用（B）では WCAG 2.2 AA が前提であり、後から直すと変更が全画面に及ぶ | 公開の前 |
| 3 | **権限と役割**（閲覧者 / 解析者 / 責任者 / 監査担当）、権限のない機能を消さずに「権限なし（申請方法）」を出す画面 | 複数の人がデータを触るようになると、誤操作と情報漏えいの影響が大きくなる | 共同研究者・自治体・顧客が使う前 |
| 4 | **監査ログと変更の承認**（下書き → 申請 → 承認、差分の提示、理由の入力） | 公的な算定値や有料レポートの数値を変えるとき、誰がいつ何を変えたかを示す必要がある | 結果を外部に公表・販売する前 |
| 5 | **スコープバー**（組織 › プロジェクト › 環境）と、スコープを含む URL | 複数の組織・複数の環境（本番 / 検証）を扱う段階で必要になる。それまでは過剰 | 2つ以上の組織が同じ基盤を使う時点 |
| 6 | SSO（SAML / OIDC）、SCIM、組織ごとのテーマ（`--brand-accent` の差し替え）、ビジュアル回帰テスト、国際化 | 大企業・多組織の運用で求められる。研究段階では費用に見合わない | 企業・自治体との契約が見えた時点 |

- 公共利用（B）に進む場合は、2（アクセシビリティ）を最優先にし、4（監査）を早める。
- 商用化（C）に進む場合は、1 と 3 を先にし、4 は有料プランの Team 以上から入れる。C の `design-system.md` §10 の「C × D で追加すること」と同じ順序を使う。
- どの場合も、C のダークパターン禁止と WCAG 2.2 AA は譲らない。

## 9. 研究データを公開リポジトリに入れない方針と UI 設計の関係

`existing-projects-analysis.md` は次の緊張関係を指摘している。**GitHub Actions は公開リポジトリにコミットしたファイルしか受け付けないが、AUDIT は「非公開データを入れない」と定めている。** このため、実データで試すには CI ではなくローカル CLI を使うしかなく、「試したいが入れてはいけない」という利用者を迷わせる構造になっている。UI はこの構造を解消する方向で設計する。

| 方針 | UI 設計での具体策 |
|---|---|
| データは手元から出さない | 第1段階の UI はローカル完結にする（静的 HTML はブラウザのファイル選択で読む。Streamlit はローカルで起動する）。アップロード先のサーバーを作らない。外部への計測送信をしない |
| どのデータを使っているかを常に見せる | 画面上部に「ローカルのデータ」「サンプルデータ（公開可）」のどちらを開いているかを、文字とアイコンで常に表示する。サンプルとの取り違えを防ぐ |
| 来歴はハッシュで示し、データ本体は見せない・出さない | 根拠パネルには SHA-256 とファイル名・版を出す。共有用の書き出しは、既定で「結果とハッシュのみ（元データなし）」にし、元データを含める場合は明示の選択を求める |
| コミットの事故を防ぐ | UI が書き出すファイルの既定の保存先を、`.gitignore` 済みのディレクトリ（例: `ui/*/local-data/`）にする。画面にも「このフォルダはリポジトリに入りません」と書く |
| CI では公開できるデータだけを使う | UI の検査（axe-core、表示確認）は、`examples/` のデモ JSON などの公開可能なサンプルだけで行う。実データを使う検査は手元で行う |
| 公開する段階では「公開してよい値」を UI で区別する | B・C に進んだとき、公開する値（集計値・係数の出典）と非公開の値（元の測定データ）を、トークン上の別の状態（例: 「公開」「非公開」のラベル）で区別し、公開操作は D の承認の流れを通す |
