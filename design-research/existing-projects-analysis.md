## 2. プロジェクト①: Math IR 多エンジン検証パイプライン（`math_interop_v0/` と関連ワークフロー）

### 実際に読んだファイル
- `math_interop_v0/README.md`, `README-phase2.md`, `README-phase3.md`, `README-phase4.md`, `README-unified.md`, `FINAL_AUDIT.md`, `UNIFIED_AUDIT.md`
- `math_interop_v0/phase1.py`〜`phase5.py`, `phase3_matlab.m`: 関数一覧と CLI の分岐部分を `grep` で確認した。全行の精読はしていない
- `.github/workflows/math-ir-phase1.yml`〜`phase4.yml`, `math-ir-unified.yml`: トリガー・ジョブ構成・保持期間を抽出して確認した

### 本来の目的
同じ数式データを、文章で書き写さずに複数の数学エンジン（SymPy / NumPy / SciPy / mpmath / DuckDB / SageMath / MATLAB の7種類）の間で受け渡す。そのうえで、厳密な有理数・仮定・単位ラベル・SHA-256 が失われないことを CI で実証する。README は「建築LCA研究本体とは完全に分離した数学計算基盤の実証実験」と位置づけている。

### 主な利用者
リポジトリの所有者本人（研究者・学生）と、その指示で作業する AI コーディングエージェント。AUDIT には「Claude Code が研究作業を進める際…」「次回再開するときは、まずこの報告書と各CIの成功ログを確認」とあり、**人間とエージェントが共同で運用する前提**が見て取れる。

### 現在の機能（実際の形態）
- **形態はライブラリ兼 CLI 兼 GitHub Actions**。GUI はない。
- `phase1.py produce/sage/verify/self-test/tamper-test`、`phase2.py run/verify`、`phase3.py prepare/verify/negative`、`phase4.py run/audit`、`phase5.py prepare/finalize/audit` という位置引数の CLI。
- Math IR 0.1 という制限付き JSON AST（integer / rational / symbol / add / mul / pow）。`eval` は使わない。
- 段階ごとの CI（PR 時と手動実行）。統合版は4ジョブ・43ノードの DAG で、9種類の改ざんを拒否する（UNIFIED_AUDIT の記載による）。
- 成果物の保持期間は 7日（第1〜4段階）または 1日（統合版）。

### 現在の操作体験の評価

**長所**
- 不明な演算・不正な数値を「安全側に拒否」し、PASS/FAIL の行をログに明示する（例: `UNIFIED SEVEN ENGINES: PASS 43 nodes…`）。合否が一目で分かる。
- 「できたこと」と「未実装」を AUDIT が丁寧に分けている。誤解を防ぐ文書としての品質は高い。
- 厳密値・近似値・誤差を別フィールドに分けて保存しており、データ来歴（provenance）を表示する UI の素材がそろっている。

**問題点**
- ルートの `README.md` は実質的に空（3バイト）で、入口がない。どの README から読めばよいか分からない。
- ワークフローが10本あり、似た名前（Phase1〜4、Unified、Efficient など）が並ぶ。「どれを押せばよいか」の判断に負担がかかる。
- 結果は Artifact の JSON（分子・分母の文字列）と CI ログだけで、人が読むための表示がない。Artifact の保持は 1〜7日で、後から結果を見返せない。
- 扱える式は合成5件などに限られる。研究者が自分の式を試すには JSON AST を手で書く必要がある。

### 4分類
**A（主）＋ D（部分的に適用済み）**。
- A の理由: 研究室内部の検証基盤であり、利用者は所有者本人と協働エージェントに限られる。
- D の理由: 監査文書・改ざん検出・バージョン固定・失敗時の安全側停止は、大企業品質の要素を先取りしている。一方、AUDIT 自身が挙げる未対応点がある（アクセス管理・電子署名・永続保存・性能評価）。D を名乗るにはこれらが足りない。
- B・C は現時点では当てはまらない。将来 B に使うなら、公的な算定結果の再現性を示す裏方の仕組みとしてになる。

### UI を付ける場合に活かせる範囲と変更コスト
- **活かせるもの**: `result.json` と `unified_graph.json`（ノード・依存関係・エンジン版・ハッシュ）は、そのまま DAG の可視化や来歴パネルのデータ源にできる。`phase1.check_envelope` は UI の入力検証にそのまま再利用できる。
- **読み取り専用ビューアは「小」**。成果物 JSON を読み込んで表やグラフで描くだけなので、計算コードには手を入れずに済む。
- **UI から SageMath/MATLAB を起動する対話型にすると「大」**。GitHub Actions のディスパッチ、MATLAB ライセンス、成果物の永続化を設計し直す必要がある。

### 将来の可能性
- 研究利用: 高い。計算の再現性や、エンジン間で結果が一致することを論文の補足資料として示す用途に向く。
- 公共利用: 公的な算定ツールの「検算エンジン」として使える可能性がある（推測）。
- 商用化: 単体では難しい。これは利用者向けの機能というより内部品質を保証する仕組みである。

### 推奨する UI 化の第一歩（最小構成）
`unified_graph.json` / `result.json` を読み込むだけの**静的 HTML ビューア**を1枚、新規ファイルとして作る。内容は次の4点。
- ケースごとのエンジン一致表
- 依存グラフ
- ハッシュと仮定・単位の一覧
- AUDIT の「未実装範囲」を常時表示する注意帯

既存の Python とワークフローは変更しない。

## 3. プロジェクト②: LCA 数学演算子と軽量 Math IR（`math_tools_v2/`）

### 実際に読んだファイル
- `math_tools_v2/README.md`, `README-operators.md`, `AUDIT.md`, `AUDIT-operators.md`, `requirements.txt`
- `math_tools_v2/lca_ops.py`（全482行を精読）
- `math_tools_v2/test_lca_ops.py`（全行）
- `math_tools_v2/portable.py`（冒頭80行と CLI 部分。関数一覧は `grep` で確認）
- `math_tools_v2/examples/lca_ops_demo.json`（冒頭とタスク ID・演算の一覧）、`examples/six_cases.json`（冒頭）
- `.github/workflows/math-ir-efficient.yml`, `math-ir-lca-operators.yml`（全文）

### 本来の目的
- `portable.py`: 既存の7エンジン検証を1ジョブに軽量化し、1〜20件の入力を扱えるようにする。
- `lca_ops.py`: 建築LCA向けの4演算を、安全な JSON 入口から実行する。4演算は次のとおり。
  - 定積分・不定積分
  - 区分的な時間関数
  - マスク付き積和（数量×排出係数×0/1マスク）
  - 節点スペクトル候補（初期・周期交換・連続排出を時間軸で累積）
- README には「本研究の正式な節点スペクトルとの一般的同値性は未証明」とある。現状は**候補モデル**の実装である。

### 主な利用者
建築LCA の研究者本人（数式・係数を厳密に検算したい人）と、協働エージェント。

### 現在の機能（実際の形態）
- **純粋関数のライブラリ兼 CLI**。`lca_ops.execute(bundle: dict) -> dict` が中核で、ファイル入出力をしない純粋関数になっている。
- CLI は `lca_ops.py run INPUT OUTPUT` と `verify INPUT OUTPUT`。verify は独立に再計算して完全一致を確認する。既存の出力ファイルは上書きを拒否する。
- 出力には次が含まれる。
  - タスクごとの `task_sha256` / `result_sha256`、全体の `input_sha256`
  - 厳密有理数、または「記号式＋小数」
  - SciPy / mpmath による数値照合
  - 端点の扱い（`endpoint_policy`）
  - イベント一覧
- 単位は10種類の固定リスト（例: `kg`, `kgCO2e`, `year`, `kgCO2e/kg`, `m2`）で次元を計算する。
- GitHub Actions の `Math IR Efficient` で mode に `lca-operators` を選ぶと実行できる（入力は `math_tools_v2/examples/` 直下のコミット済みファイルに限られる）。
- 合成例の期待値（README とテストの記載）: 12kg×1/3=4kgCO2e。評価期間20年で、終端の交換を除くと48、含めると52kgCO2e。区分時間積分は50kgCO2e。

### 現在の操作体験の評価

**長所**
- 入力の検査が厳格で、拒否するケースのテストが充実している。テストで確認されている拒否は、不正な演算、ゼロ除算、単位不一致、時間区間の欠落、マスクが0/1以外、参照先なし、周期0、特異点、未知のフィールド。
- 「係数を基準計算から逆算しない」という方針がコードとテストで担保されている。研究倫理の面で信頼できる。
- 端点の扱い（20年目の交換を含むか）が明示的な真偽値で、結果にも記録される。UI で切り替えて比べる操作と相性がよい。
- 依存のバージョンが固定され（`requirements.txt`）、CI は Python だけで完結する。SageMath も MATLAB も不要なので起動が軽い。

**問題点**
- **JSON AST が人にとって冗長**。`t^2` だけで約14行になる。研究者が自分の式を入れるには、手で AST を書くか別ツールが必要。
- **エラーメッセージが英語で、場所が特定しにくい**。例えば `integral task: unexpected or missing fields` は、どのフィールドが余分または不足かを示さない。
- `--help` がない。使い方は README の CLI 例にしかない（自前の `sys.argv` 分岐で、引数違いは Usage を1行出すだけ）。
- **GitHub Actions は公開リポジトリにコミットしたファイルしか受け付けない。** 一方で AUDIT は「非公開データを入れない」と定めている。このため、実データで試すには CI ではなくローカル CLI を使うしかない。「試したいが入れてはいけない」という、利用者を迷わせる構造になっている。
- 結果は分子・分母の文字列 JSON だけで、時系列のグラフやイベントのタイムラインが見えない。

### 4分類
**現在は A ＋ D(部分)。将来の選択肢として B ＋ D。C は条件付き。**
- A の理由: 研究者本人が自分の候補モデルを検算する道具だから。
- B の可能性: 建築物の LCA を公共の場で比較・算定する用途では、透明性（係数の出所・来歴ハッシュ・端点ルールの明示）が最重要になる。この実装の思想はそこに合う。ただし、それには候補モデルを研究として確立することと、単位系・係数データベースの整備が前提になる。
- C の条件: 設計事務所向けの有料 SaaS などは、入力 UI・係数データベース・サポート体制がないと成り立たない。現状からの距離は大きい。
- D の理由: B または C に進む場合、アクセス制御・永続保存・監査ログ・多言語の誤りメッセージ・アクセシビリティが必須になる。

### UI を付ける場合に活かせる範囲と変更コスト
- **`execute(bundle)` をそのままバックエンド API にできる**（FastAPI や Streamlit から関数として呼ぶ）。純粋関数なので**変更コストは「小」**。
- **来歴表示は「小」**。`input_sha256` / `task_sha256` / `result_sha256` / `verification_level` / `interpretation` を「この結果の出所」パネルにそのまま出せる。
- **入力フォームは「中」**。
  - `masked_sum_product`（数量・係数・マスク）と `node_spectrum`（周期・評価期間・端点）は、表形式のフォームから JSON を組み立てやすい。
  - 任意の式（AST）の入力には、数式エディタか、制限付き構文解析器を別途用意する必要がある。
  - いずれも `lca_ops.py` 本体を変えずに外側で作れる。
- **誤りメッセージの日本語化と場所の特定は「小〜中」**。`ValueError` の文言を UI 側の対応表で翻訳する。フィールド名を出すなら `exact_keys` の改修が必要になる。
- **非公開データの扱いは「中」**。ローカル実行型の UI にすれば、公開 CI に流さずに済む。

### 将来の可能性
- 研究利用: 高い。候補モデルの感度分析（周期・評価期間・端点の切り替え）を UI で比較すれば、研究そのものを支援できる。
- 公共利用: 中。モデルの確立と係数データの出所が条件。
- 商用化: 低〜中。係数データベースや BIM 連携など、別に大きな投資が要る。

### 推奨する UI 化の第一歩（最小構成）
**ローカルで動く1画面の「LCA 演算子プレイグラウンド」**を新規ファイル1つ（例: Streamlit の `ui_app.py`）で作る。
1. `examples/lca_ops_demo.json` を初期値として読み込む。
2. 係数（数量・排出係数・マスク）と `node_spectrum` のパラメータ（周期・評価期間・`include_end`）だけをフォームで編集できるようにする。
3. `lca_ops.execute()` を呼び、合計（例: 48↔52 kgCO2e）、イベントのタイムライン、ハッシュ、注意書き（候補モデルであること）を表示する。
4. 結果 JSON をダウンロードできるようにし、`lca_ops.py verify` で検算できる導線を残す。

`lca_ops.py` には手を入れない。データはローカルにとどまるので、公開 CI の制約とも衝突しない。

## 4. プロジェクト③: Dropbox OAuth 自動登録（`scripts/dropbox_auth_manage.py` ほか）

### 実際に読んだファイル
- `scripts/dropbox_auth_manage.py`（全文）
- `docs/DROPBOX_AUTH_FAST_SETUP.md`（全文）
- `.github/workflows/dropbox-auth.yml`（全文）
- `git log --oneline`（直近20件の件名）

### 本来の目的
Dropbox の認可コードを GitHub Actions 上でリフレッシュトークンに交換する。Dropbox への実際の書き込みとハッシュの一致を確かめたうえで、トークンを暗号化して GitHub Actions Secret に保存する。将来、計算結果を Dropbox に保存するための下準備である（docs によれば、計算結果の転送版は別ブランチにある。そのブランチは本調査では確認していない）。

### 主な利用者
リポジトリの所有者本人1名。初回設定のときに1回だけ使う。

### 現在の機能（実際の形態）
- 手動実行のワークフロー（mode: `preflight` / `exchange`）と、それが呼ぶ Python スクリプト。
- 資格情報をログに出さない設計になっている。HTTP エラーは状態コードだけを返し、本文を返さない。リポジトリ名が一致しなければ停止する。

### 現在の操作体験の評価

**長所**
- preflight → exchange の2段階で、失効しやすい認可コードを無駄にしないよう手順が組まれている。
- 成功時に「次にどの一時 Secret を削除すべきか」まで表示し、後片付けへ誘導する。
- 誤りメッセージが行動を促す内容になっている（例: 権限不足の場合に必要な権限を示す）。

**問題点**
- 手順が、GitHub 設定画面・Dropbox 認可 URL・Actions 実行画面の3か所にまたがる。認可コードの有効期限は短く、時間に追われる作業になる。
- 手順書は docs の Markdown にしかなく、ワークフロー実行画面からはたどれない。
- 個人用の手順に強く依存しており、別のメンバーや別のリポジトリでは再利用しにくい（リポジトリ名を固定している）。

### 4分類
**A（内部運用ツール）。セキュリティの観点で D の基準を部分的に満たす。** 独立したアプリではなく、研究基盤の運用を補助するものである。

### UI 化の範囲と変更コスト
- 独自の Web UI は**推奨しない**。資格情報を扱う画面を増やすと攻撃面が広がる。
- 改善は**「小」**で済む。ワークフローのジョブサマリーに次の手順と所要時間の目安を出す、docs をチェックリスト形式にする、の2点。

### 推奨する第一歩
`docs/DROPBOX_AUTH_FAST_SETUP.md` を「チェックリスト＋各ステップの所要時間＋失敗時の対処」形式に整理する。コードは変更しない。

## 5. プロジェクト④: 単体実行ワークフロー（`matlab-run.yml` / `sagemath-run.yml`）

### 実際に読んだファイル

### 目的・形態
手動実行の入力欄に MATLAB または SageMath のコマンド文字列を書き、クラウドで実行して出力を Artifact に保存する。**ローカルにインストールせずに数式処理系を使うための窓口**である。

### 操作体験の評価
- 長所: ブラウザだけで MATLAB の記号計算を試せる。既定値に例題（`x^2*sin(x)` の積分）が入っているので、初回の操作に迷わない。
- 問題点:
  - 結果を見るには Artifact をダウンロードして開く必要があり、往復に時間がかかる。
  - 入力欄が1行なので、複数行のスクリプトを書きにくい。
  - **`matlab-run.yml` は入力をコマンド文字列に直接埋め込んでいる**（`${{ inputs.command }}`）。sagemath 版は環境変数を経由している。手動実行には書き込み権限が要るので影響は限られるが、D の品質基準では修正対象になる。FINAL_AUDIT も「任意コマンド起動機能を有効にしているので、アクセス権限と入力内容の管理を要する」と認めている。

### 分類と第一歩
**A**。UI 化は不要で、ジョブサマリー（`$GITHUB_STEP_SUMMARY`）に結果を直接書き出すだけで操作体験が大きく改善する（変更コスト「小」）。

### 6.2 空気清浄度（室内空気質）関連アプリ: **見つからなかった**
見立てとして、用途によって適用すべき分類が分かれる。

- 学校・公共施設の空気質を広く見せる場合 → **B＋D**。アクセシビリティ、閾値の根拠表示、多数の拠点の運用、長期の可用性が必要。
- 一般家庭・テナント向けの監視サービス → **C＋D**。初回設定の易しさ、通知設計、課金、プライバシー（在室推定などの個人情報）が要点。

## 7. 横断的な所見（UI/UX 研究への示唆）

1. **共通の強み: 「信頼できる計算」の素材がそろっている。** 厳密値と近似値の分離、来歴ハッシュ、未実装範囲の明示、安全側の拒否がある。UI ではこれを「結果の信頼度パネル」として前面に出せる。これは B と D で特に価値が高い。
2. **共通の弱み: 入口と結果表示がない。** 空の README、10本のワークフロー、短期間で消える Artifact、英語のエラーが重なり、操作の起点と結果の見返しが弱い。
3. **公開リポジトリ CI と非公開研究データの緊張関係。** 実データで試すにはローカル実行型の UI が必要になる。研究支援（A）の UI は「ローカル完結」を第一の原則にするのが妥当。
4. **人間と AI エージェントの共同運用。** AUDIT は人とエージェントの両方に向けて書かれている。UI 設計でも、人が読む表示と、エージェントが読む機械可読 JSON を分けずに両立させる方針が合っている。
